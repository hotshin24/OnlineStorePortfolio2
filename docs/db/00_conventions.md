# 00. DB 공통 설계 규칙

> 대상: 자체 브랜드 패션 온라인몰 (2020년 런칭, 7년차, 연매출 4,700억 원, 국내·해외 생산)
> 기술 스택: Oracle Database (19c 호환 문법, 로컬은 Oracle Free 23ai) / Spring Boot + JPA / Flyway

## 1. 규모 가정

| 항목 | 가정치 | 산출 근거 | 설계 영향 |
|---|---|---|---|
| 연 주문 수 | 약 470만 건 | 4,700억 원 ÷ 객단가 약 10만 원 | 주문·결제 테이블 월 단위 파티션 |
| 일 주문 수 | 평균 약 1.3만 건, 최대 약 10만 건 | 블랙프라이데이·시즌오프 기준 | 재고 예약 동시성 제어 |
| 누적 주문 (7년) | 약 2,500만 건 | 매출 성장 곡선 반영 | 주문 이력 조회용 인덱스 |
| 누적 주문 상품 | 약 5,000만 행 | 주문당 평균 2개 | 파티션, 집계 테이블 분리 |
| 누적 회원 | 약 400만 명 (활성 약 150만 명) | | 휴면 회원 분리 보관 |
| 스타일 (품번) | 누적 약 1.5만 개 | 연 4시즌 × 약 2,000개 + 캐리오버 | |
| SKU | 누적 약 30만 개 | 스타일당 평균 컬러 3개 × 사이즈 6개 | 재고는 창고 × SKU 단위 |
| 생산 발주 | 연 약 3,000건 | 국내 40%, 해외 60%(베트남·중국·방글라데시) | 외화, 환율, 통관 관리 |

## 2. 데이터베이스 기본 규칙

- **문자셋**: `AL32UTF8`. 길이는 문자 단위로 선언한다(`VARCHAR2(n CHAR)`).
- **스키마**: 하나의 스키마(`FSHOP`)를 쓰고, 도메인은 테이블 접두어로 구분한다.
- **19c 호환**:
  - `BOOLEAN` 대신 `CHAR(1)`을 쓰고 `CK_*_YN CHECK (X IN ('Y','N'))` 제약을 건다.
  - 23ai 전용 문법(`IF NOT EXISTS`, JSON Relational Duality 등)은 쓰지 않는다.

## 3. 네이밍 규칙

| 대상 | 규칙 | 예시 |
|---|---|---|

| 컬럼 | 대문자 snake_case | `ORDER_NO`, `SALE_PRICE` |

## 4. 키 전략

- **PK**: `NUMBER(19) GENERATED BY DEFAULT AS IDENTITY` 대리키. JPA에서는 `@GeneratedValue(strategy = IDENTITY)`로 매핑한다.
  - 대량 INSERT가 많은 테이블(`ORD_ORDER_ITEM`, `INV_STOCK_TXN`, 로그류)은 `SEQUENCE` + `allocationSize=50`으로 바꿀 수 있게 열어 둔다(V2 검토).
- **업무 키**: 외부에 노출되는 번호는 대리키와 별도로 UK를 둔다.
  - 주문번호 `ORDER_NO`: `YYYYMMDD` + 10자리 일련번호. 예: `202611200000012345`
  - 품번 `STYLE_CD`: 브랜드 + 시즌 + 복종 + 일련번호. 예: `AB26FTS0012`
  - SKU 코드 `SKU_CD`: `STYLE_CD` + 컬러 + 사이즈. 예: `AB26FTS0012-BK-M`
  - 발주번호 `PO_NO`: `PO` + 연월 + 일련번호. 예: `PO2611-00321`
- **외부 노출 금지**: 대리키(`*_ID`)는 URL과 API에 그대로 노출하지 않는다. 업무 키나 별도 공개 키를 쓴다.

## 5. 공통 컬럼

모든 테이블에 붙는다. 단, 순수 로그와 원장 테이블은 `CREATED_*`만 둔다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `CREATED_AT` | `TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL` | 생성 일시 |
| `CREATED_BY` | `VARCHAR2(50 CHAR)` | 생성자 (회원 ID, 관리자 ID, `SYSTEM`, 배치명) |
| `UPDATED_AT` | `TIMESTAMP` | 수정 일시 |
| `UPDATED_BY` | `VARCHAR2(50 CHAR)` | 수정자 |

- JPA에서는 `BaseTimeEntity`와 `BaseEntity`(`@MappedSuperclass`, `AuditingEntityListener`)로 채운다.
- 동시 수정이 일어나는 테이블(재고, 쿠폰 수량, 적립금 잔액)에는 `VERSION NUMBER(10) DEFAULT 0`을 두고 `@Version`으로 낙관적 락을 건다.

## 6. 삭제·이력 정책

| 데이터 유형 | 정책 |
|---|---|
| 거래 데이터 (주문, 결제, 클레임, 재고 원장, 정산) | 물리 삭제·수정 금지. 정정은 반대 거래(역분개)로 기록한다. |
| 마스터 데이터 (상품, 쿠폰, 업체) | `USE_YN` 또는 `DELETED_AT`으로 논리 삭제한다. |
| 상태가 바뀌는 엔티티 (주문, 클레임, 발주, 입출고) | 현재 상태는 본 테이블에, 변경 이력은 `*_STATUS_HIST`에 저장한다. |
| 가격 | `PRD_PRICE_HIST`에 적용 기간(`START_AT`, `END_AT`)으로 관리한다. 주문 시점 가격은 주문 상품에 스냅샷으로 남긴다. |
| 탈퇴 회원 | 개인정보는 즉시 파기(NULL 처리)한다. 거래 기록은 전자상거래법 보관 기간(5년)만큼 비식별 상태로 남긴다. |

## 7. 금액·통화

- 원화 금액은 정수 `NUMBER(15)`로 저장한다(최대 999조).
- 외화는 `{항목}_FC_AMT NUMBER(18,4)`에 `CURRENCY_CD CHAR(3)`(ISO 4217)과 적용 환율 `EXCHANGE_RATE NUMBER(15,6)`을 같은 행에 저장한다. 원화 환산액 `{항목}_AMT`도 함께 저장한다.
- 할인 배분은 원 단위에서 끝수가 생긴다. 끝수는 금액이 가장 큰 주문 상품에 몰아 합계가 정확히 맞게 한다.
- 금액 CHECK 제약: `CK_*_AMT CHECK (X >= 0)`. 음수가 필요한 원장은 `AMT`와 함께 증감 구분 코드(`TXN_TYPE`)를 둔다.

## 8. 코드값 관리

| 구분 | 방식 | 예시 |
|---|---|---|
| 상태처럼 로직이 걸린 고정 코드 | `VARCHAR2(30 CHAR)` + CHECK 제약 + JPA `@Enumerated(EnumType.STRING)` | 주문 상태, 결제 수단, 클레임 유형 |
| 운영자가 추가·수정하는 코드 | `CMM_CODE_GROUP` / `CMM_CODE` 테이블 | 반품 사유, 소재 코드, 컬러 코드, 은행 코드 |

- 코드값은 영문 대문자 snake_case로 쓴다. 예: `PAYMENT_COMPLETED`.

## 9. 개인정보 보호

| 항목 | 저장 방식 |
|---|---|
| 비밀번호 | BCrypt 단방향 해시 (`PASSWORD_HASH`) |
| 이름, 휴대폰, 이메일, 주소, 환불 계좌 | AES-256 양방향 암호화 (`*_ENC`, 평문 길이의 약 2배 이상 확보) |
| 로그인·중복 확인용 검색 | SHA-256 + 솔트 해시 컬럼 (`EMAIL_HASH`, `PHONE_HASH`)에 UK 또는 인덱스 |
| 휴면 회원 (1년 미접속) | 개인정보를 `MBR_DORMANT`로 옮기고 `MBR_MEMBER`의 개인정보 컬럼은 NULL 처리 |
| 관리자 개인정보 조회 | `SYS_AUDIT_LOG`에 접속 기록을 2년 이상 보관 |

- 암호화와 복호화는 애플리케이션에서 JPA `AttributeConverter`로 처리한다. DB는 암호문만 저장한다.

## 10. 파티셔닝 · 인덱스

- **파티션 대상**: 월 단위 `INTERVAL` RANGE 파티션.

  | 테이블 | 파티션 키 |
  |---|---|
  | `ORD_ORDER`, `ORD_ORDER_ITEM` | `ORDER_AT` |
  | `PAY_PAYMENT` | `REQUESTED_AT` |
  | `INV_STOCK_TXN` | `TXN_AT` |
  | `SYS_AUDIT_LOG`, `SYS_NOTIFICATION_LOG` | `CREATED_AT` |

  - 자식 테이블(`ORD_ORDER_ITEM`)은 부모의 파티션 키를 중복 저장한다. 참조 파티셔닝은 JPA와 마이그레이션 복잡도 때문에 쓰지 않는다.
- **인덱스 원칙**:
  - 모든 FK 컬럼에 인덱스를 만든다. Oracle은 FK에 인덱스가 없으면 부모 테이블 DML 시 테이블 락이 걸린다.
  - 조회 조건 순서는 동등 조건 → 범위 조건이다. 예: `IX_ORD_ORDER_MEMBER_DT (MEMBER_ID, ORDER_AT DESC)`.
  - 파티션 테이블에는 LOCAL 인덱스를 기본으로 쓰고, 업무 키 UK만 GLOBAL로 만든다.

## 11. 마이그레이션 · JPA 매핑

- 경로: `backend/src/main/resources/db/migration/V{번호}__{도메인}.sql`
- DDL 소유권은 Flyway에 있다. JPA는 `spring.jpa.hibernate.ddl-auto=validate`로 둔다.
- 연관관계: 기본은 `@ManyToOne(fetch = LAZY)` 단방향이다. 집합 관계(`@OneToMany`)는 주문 → 주문 상품처럼 생명주기가 같은 경우에만 쓴다.
- 다른 도메인 간 참조(예: 주문 → 상품)는 FK 제약은 걸되, 엔티티는 ID 값으로만 참조한다. 이렇게 하면 도메인 경계를 유지할 수 있다.
