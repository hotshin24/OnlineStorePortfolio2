# 진행 메모

`CLAUDE.md`의 "진행 상황"에서 옮긴 도메인별 세부 기록이다 (2026-11-27 정리). `CLAUDE.md`에는 단계, 숫자, 다음 할 일만 남겼다. 결정 경위는 결정 PDF(`docs/pdf/결정/`), 다른 도메인으로 넘긴 일은 정책명세의 넘김 사항(`tools/pdfgen/policy/*_content.py`의 `HANDOFF`)이 기준이다.

## 공통

- 법률 검토 L10~L12는 회원 컬럼 검토 C-82~C-90, C-72~C-74·C-77~C-79, C-93~C-96과 같은 결정이다.

## 1차 범위 (2026-11-28 사용자 결정)

6개 도메인을 한꺼번에 확정하지 않고, 코드로 처음 구현할 범위(1차)부터 컬럼을 확정한다. 외부 검토 2개를 결정과 대조해 정리했고, 질문 4개에 답을 받았다 (1 A, 2 A, 3 A, 4 A). 이어서 외부 검토로 테이블 6개와 공통 2개를 보충했다 (1차-5 A).

- 1차 흐름: 이메일 가입(본인인증 포함) → 상품 등록·승인·조회 → 장바구니 → 주문 생성과 재고 예약 → 카드·간편결제 승인(PG 1곳), 실패·만료 때 예약 해제 → 할당과 출고 요청 → 출고(실물 차감, 수불 원장) → 운송장·배송 추적. 전제: 창고 1곳(WMS 없음), 택배사 1곳, 원화 국내 배송.
- 1차-1 A 취소: 1차는 결제 자체 사유의 자동 취소만 연다(만료 뒤 승인, 금액 불일치). 고객 취소·반품·교환은 2차에 클레임 도메인과 함께 연다. 환불 요청의 근거가 클레임 ID·주문 변경 이력·결제 자체 사유 중 정확히 하나여야 하기 때문이다(결제 1-3 A).
- 1차-2 A 재고 시작: 기초 재고로만 시작한다(IC-79 A). 입고 예정과 생산 입고는 2차(SCM과 함께).
- 1차-3 A 배송지: 회원 주소록(`MBR_DELIVERY_ADDRESS`)을 1차에 둔다.
- 1차-4 A 컬럼 확정 범위: 1차 흐름이 쓰는 컬럼과, 흐름과 상관없이 나중에 바꾸기 비싼 것(PK·UK·FK, 파티션 키, NOT NULL과 기본값, 상태 코드·전이, 여러 컬럼 CHECK, 암호화·해시 컬럼)을 1차에 확정한다. 나머지 NULL 허용 컬럼은 그 업무를 여는 차수에 확정한다. 금액 합계 CHECK에 들어가는 컬럼은 1차에 값이 0이어도 1차다.
- 차수 표기 (사용자 결정): 정의서에서 확정 칸 옆에 차수 칸을 따로 둔다. 각 도메인 정의서를 고칠 때 넣는다. 재고는 2026-11-28에 넣었다(테이블 이름·컬럼정의서). 1차 테이블 안의 FK 6개(입고 예정 4, 보류 건, 재고 예외)는 1차-6 A로 "1차 (FK 2차)"이고, 수불 사유는 IC-96 A로 값마다 차수를 표시한다. 수불 원장에서 2차 사유만 채우는 컬럼 13개는 IC-121 A로 "1차 생성 (2차 사용)"(FK 2차 3개는 "1차 생성 (2차 사용, FK 2차)")이다. 다시 물을 것 21개 중 1차 8개는 컬럼 검토에서 확정한다(2026-11-28 IC-82~IC-99 반영 뒤 고침).
- 1차 재고 한계 (IC-96 A): 원천이 1차에 없는 사유(WMS 입고·검수·처분 작업, 클레임 검수, 입고 예정, 보류 건, 재고 예외)는 1차에 쓸 수 없다. 1차에 쓰는 수불 사유는 판매·재발송·비주문 출고, 정상에서의 불량 전환, 불량 해제, 기초 재고뿐이라 불량은 쌓이기만 하고(처분·수선은 2차) 보류·실사 조정도 2차다. 반송 재발송과 반송 입고·검수도 2차이고 가상 데이터에 반송 상태를 만들지 않는다.
- 1차 테이블 49개 (1차-5 A로 43 → 49, 1차-6~8 A는 테이블 수를 바꾸지 않음):
  - 회원 10: `MBR_MEMBER`, `MBR_JOIN_ATTRIBUTION`(가입 때 같은 트랜잭션, 본인인증 생년월일로 채우는 `JOIN_AGE_GROUP_CD` NOT NULL), `MBR_LOGIN_ACCOUNT`, `MBR_IDENTITY_VERIFICATION_LOG`(CI 1인 1계정), `MBR_GRADE`(기본 등급 1행), `MBR_DEVICE`, `MBR_REFRESH_TOKEN`, `MBR_CONSENT`, `MBR_CONSENT_HIST`, `MBR_DELIVERY_ADDRESS`.
  - 상품 11: `PRD_BRAND`, `PRD_SEASON`, `PRD_CATEGORY`, `PRD_COLOR`, `PRD_STYLE`, `PRD_STYLE_COLOR`, `PRD_SKU`, `PRD_STYLE_MEDIA`, `PRD_PRICE_CHANGE_REQUEST`, `PRD_PRICE_HIST`, `PRD_DISPLAY_CONTENT_HIST`(구매 전 고시·고지).
  - 주문 4: `ORD_CART`, `ORD_ORDER`, `ORD_ORDER_ITEM`, `ORD_ORDER_ITEM_STATUS_HIST`.
  - 결제 8: `PAY_PAYMENT`, `PAY_PAYMENT_METHOD_PG_SETTING`, `PAY_CARD_MERCHANT_CONTRACT`(승인 때 정산 방식 NOT NULL, PYC-74 A), `PAY_PG_CODE_MAPPING`(카드사·실패 코드, PYC-2 B·PYC-37 A), `PAY_PG_API_LOG`, `PAY_PG_WEBHOOK_INBOX`(7-2 A), `PAY_REFUND_REQUEST`, `PAY_PAYMENT_CANCEL`(자동 취소).
  - 재고 6: `INV_STOCK`, `INV_STOCK_COMMITMENT`, `INV_STOCK_COMMITMENT_EVENT`(IC-10 B), `INV_STOCK_LEDGER`(기초 재고 사유 포함), `INV_SAFETY_STOCK_HIST`(새 행 기본값 이력), `INV_MONTHLY_CLOSING`(원장 업무 일자의 달이 열려 있는지 검사, 8-2 C).
  - 배송 10: `DLV_COURIER_RATE`(포장 때 운임 4개와 함께 채움, CHECK), `DLV_SHIPMENT_REQUEST`, `DLV_SHIPMENT_REQUEST_ITEM`, `DLV_SHIPMENT`, `DLV_WAYBILL`, `DLV_WAYBILL_ITEM`, `DLV_STATUS_HIST`, `DLV_TRACKING_EVENT`, `DLV_COURIER_INTERFACE_LOG`, `DLV_REMOTE_AREA_POSTCODE`(주문 5-7 A).
- 공통·관리자 (미설계, 1차 전에 최소 설계, 이름은 후보): 외부 업체 마스터 `SYS_EXTERNAL_VENDOR`(본인인증 업체, 택배사, PG), 상태 이력 `SYS_STATUS_HIST`(상품 판매 등록 검수 상태 등, 선행 6), 공통코드와 전 도메인 `CODE_ID` 발번, 영업일 달력(주문 1-8 A), 인증번호 `SYS_VERIFICATION_CODE`, 관리자, 개인정보 접속 기록, 배치 잠금. 중복 방지 키는 각 행에 있으므로(`ORDER_REQUEST_KEY_VAL`, `SHIPMENT_REQUEST_KEY_VAL`, `LEDGER_KEY_VAL`) 별도 테이블은 공통 설계 때 정한다.
- 도메인을 가로질러 함께 정할 것: 주문 생성과 재고 예약은 한 트랜잭션(재시도는 주문 요청 키, 마지막 1개 동시 주문은 판매 가능 CHECK), 결제 승인과 주문 만료 경합 때 주문 상태 재확인(승인 → 할당·출고 요청, 실패·만료 → 예약 해제, 만료 뒤 승인 → 자동 취소), 출고 ID 하나로 정상·할당 감소와 원장 1행(재처리는 원장 키로 한 번만).
- 1차 전에 남은 일: 회원 `MBR_CONSENT`·`MBR_CONSENT_HIST` 보류 해제, 주문 답변 전 OC 13개, 상품 단품·세트 구분 결정.
- FK 적용 시점: 창고 FK는 WMS 설계 때 걸고 1차에는 재고·배송이 같은 창고 값을 쓴다. 1차-6 A: 부모가 2차 이후 테이블인 FK 15건(입고 예정 4, 보류 건, 재고 예외, 주문 변경 이력 3, 차지백, 법정대리인 동의, 배송 사고, 저장 결제수단, 프로모션 쿠폰 정책 2)은 컬럼과 CHECK를 1차에 만들고 FK 제약은 부모를 만드는 차수의 마이그레이션에서 `ALTER TABLE … ADD CONSTRAINT`로 건다. 정의서 차수 칸에는 "1차 (FK 2차)". 프로모션 2건은 프로모션 설계 때 값 참조로 둘지 함께 본다.
- 1차-7 A 미성년 회원 주문: 1차는 주문 생성 전에 막고 안내한다(주문 9-3 A CHECK에 걸리기 전). 법정대리인 동의 테이블과 미성년 주문은 2차.
- 1차-8 A 오픈 뒤 등록한 SKU의 첫 재고: 1차 동안 기초 재고 사유를 원장이 한 건도 없는 현재고 행에 행마다 1회 허용한다(IC-79 A 변경 안내). 같은 SKU의 재입고는 2차에 입고 예정과 함께.
- 데이터: 포트폴리오라 실제 데이터를 넣을 수 없다. 1차분 구현을 마치면 가상 데이터로 채운다(2026-11-28 사용자). 기초 재고(1차-8 A)도 가상 데이터 적재 경로로 쓴다.
- 외부 검토에서 바로잡은 점: 클레임 없이 고객 취소 불가(결제 1-3 A), 가입 본인인증은 뺄 수 없음(가입 유입 경로의 NOT NULL 연령대. 처음에 `MBR_MEMBER` 컬럼으로 잘못 적었다가 1차-5 때 바로잡음), 확보 처리 이력 누락, `SYS_IDEMPOTENCY_KEY`는 정한 적 없음, 테이블 수 불일치.

## 주문 (ORD)

- 결정 번호는 `분야-순번`이다.
- 남은 것: `ORD_ORDER`의 주문 당시 회원 스냅샷, 목록 표시·행 버전 그룹과 나머지 8개 테이블.
- 답변 전인 컬럼 검토 OC-1~OC-9, OC-11~OC-14가 정의서에 추천안대로 반영된 것으로 보이는 곳(`ORD_ORDER_ATTRIBUTION`, 선물 받는 사람 컬럼 등)이 있다. 답을 받은 뒤 정의서와 대조한다 (2026-11-26 확인).
- 회원 도메인에서 넘겨받아 주문에서 정한 것:
  - 공동현관 출입 방법은 코드 + 비밀번호·기타일 때만 암호문이고, 주문 상품이 모두 구매 확정되고 회수가 없으면 NULL (5-8 B, OC-100 A, OC-105 A, 회원 C-71).
  - 미성년 주문: 취소권 고지 일시, `LEGAL_GUARDIAN_CONSENT_ID` FK, 적용 한도와 그 달 사용액 복사 + CHECK, 회원 행 잠금 뒤 합산 (9-3 A, 9-4 A, 9-5 B, OC-120, OC-122, 회원 C-83·C-90·C-95). 파기 예정일은 max(기산일 + 5년, min(성년 도달일 + 3년, 주문일 + 10년)) (10-2 A, C-96).
  - 비회원 주문 전 본인인증 결과(업체 코드, 거래번호, 인증 일시, CI 해시)를 주문에 복사 (9-1 A, OC-83 A, 회원 C-85).

## 결제 (PAY)

- 확정: `PAY_PAYMENT`의 식별, 상태·결과, 결제 수단, 금액, PG·가맹점 그룹 (`pay/data.py`의 `CONFIRMED_GROUPS`, 2026-11-26). 남은 것: `PAY_PAYMENT`의 단계별 일시부터 미성년·요청 환경까지 12개 그룹과 나머지 20개 테이블.
- 논리명만 바꾼 용어 (물리명 그대로):
  - "운영자 확인" → "결제/취소 예외 수동 처리" (`MANUAL_CHECK_*`, PYC-58~59). 정책명세 조는 "예외 수동 처리", 관리자 화면은 "예외 처리함". 과거 결정 기록의 "운영자 확인"과 같은 뜻이다.
  - 간편결제 "내부" → "간편결제 앱에서 고른 결제 수단 코드 / 카드로 낸 금액 / 현금성으로 낸 금액" (`EASY_PAY_INNER_*`, PYC-67).
  - `PG_TRANSACTION_NO` = "PG 결제 키 (결제 단위 거래번호)" (PYC-75). 승인 거래번호는 `PG_APPROVAL_TRANSACTION_NO`.
- 다른 도메인에 걸린 것: PYC-33 A(같은 주문 안 재시도, 주문 OC-69 B와 충돌, 주문으로 넘김), PYC-80 A·PYC-86 A(공통 규칙, 지시 규칙 4).
- PYC별 결정 내용과 경위는 `pay/col_review.py`(`결제_컬럼검토_결정.pdf`)에 있다. 추천과 다르게 고른 것: 65 B, 72 A, 78 A, 79 B, 84 A, 86 A.
- PYC-6~PYC-15는 외부 검토(토스페이먼츠 결제 객체 대조)에서 나온 PG 수신 값이다. 정의서에서 PG에서 오는 컬럼은 번호를 굵게 표시한다 (`pay/data.py`의 `PG_SOURCED`).
- 즉시 할인은 부담 주체별 금액 3개(카드사, 간편결제사, PG)로 바꿨다 (PYC-11 A, PYC-15 A). 결제결정 10-1에 변경 안내가 있다.

- 제안해 둔 것: 21c XE에서 3단 참조 파티션(주문 → 결제 → 취소) 제거를 먼저 시험 (11-1 A).
