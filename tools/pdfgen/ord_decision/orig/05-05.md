## 5-5. 주문자·수령인·배송지 위치

**무엇을 정하나요?**
주문자 정보, 받는 사람 정보, 배송 주소를 **주문 테이블에 컬럼으로 둘지, 따로 테이블을 만들지**입니다.

**담을 값과 암호화 (확정 규칙 적용)**

| 그룹 | 값 | 저장 방식 |
|---|---|---|
| 주문자 | 이름 | 평문 + TDE (C-72) |
| 주문자 | 휴대폰 | 암호화 + 검색용 해시 (비회원 주문을 회원에 연결할 때 씀, 선행 14) |
| 주문자 | 이메일 | 암호화 |
| 수령인 | 이름 | 평문 + TDE |
| 수령인 | 휴대폰 | 암호화 |
| 주소 | 우편번호, 도로명·지번 주소 | 평문 + TDE (C-73) |
| 주소 | 상세 주소 | 암호화 |

공동현관 출입 방법(5-8)과 배송 요청 사항(5-6)도 이 주소에 딸린 값입니다.

**예시로 보면**
1. 회원이 저장된 집 주소를 골라 주문했습니다.
2. 출고 전에 고객센터에 전화해 회사 주소로 바꿔 달라고 합니다.
3. 한 달 뒤 회원이 마이페이지에서 집 주소를 고칩니다.

2의 변경은 주문에 반영되어야 합니다. 3의 변경은 이미 나간 주문에 영향을 주면 안 됩니다. 그래서 주문에는 회원 배송지(`MBR_DELIVERY_ADDRESS`)를 가리키지 않고 값을 복사합니다. 여기까지는 어느 선택지든 같습니다.

**선택지**

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 모두 주문 테이블 컬럼으로 둠. 배송지를 바꾸면 덮어쓰고, 이전 값은 데이터 변경 감사 로그(선행 6)에 남음 | 테이블이 늘지 않음 (규칙 5). 개인정보 보유 공통 컬럼 4개를 주문 하나에 두고 함께 파기함 | 주문 테이블 컬럼이 많아짐 (약 15개) |
| B | 주문 배송지 1:1 테이블을 따로 둠 (`ORDER_ID` 공유 PK). 주문자는 주문에 두고, 수령인·주소는 배송지 테이블에 둠 | 주문 테이블이 가벼움. 배송지만 따로 파기 규칙을 줄 수 있음 | 규칙 5 예외가 하나 더 생김 (3-6 B에 이어). 주문 조회 대부분에 조인이 붙음 |
| C | 주문 배송지 1:N 테이블을 둠. 바꿀 때마다 새 행을 넣고 현재 행을 표시함 | 배송지 변경 이력이 테이블에 그대로 남음 | 테이블 1개. "현재 행은 하나" 규칙을 지켜야 함. 변경은 드물어 대부분 행이 하나뿐임 |

**추천: A.**
- 주문과 배송지는 1:1입니다. 1:1은 규칙 5에서 테이블을 만들 이유가 아닙니다. 배송지를 나눠 보내는 기능은 운영하지 않습니다 (4-1 A).
- 배송지 변경은 드물고, 바뀐 기록은 데이터 변경 감사 로그가 맡기로 이미 정해져 있습니다 (선행 6). 그래서 C처럼 변경 이력을 위한 테이블이 따로 필요 없습니다.
- 주문 개인정보는 한꺼번에 파기합니다 (10분야). 주문자와 배송지가 같은 행에 있으면 파기 처리 하나로 끝납니다.

**4-6 B (선물하기)와의 관계**
- 선물 주문은 받는 사람이 수락할 때까지 수령인 휴대폰만 있고 주소는 비어 있습니다.
- A라면 주소 컬럼을 NULL 허용으로 두고, CHECK로 "일반 주문이면 결제 완료 이후 주소 NOT NULL, 선물 주문이면 수락 이후 NOT NULL"을 겁니다.
- 개인정보 컬럼은 원래 파기를 위해 NULL 허용이 기본이므로 (선행 7), 새로 생기는 부담은 없습니다.

**A를 고르면 주문 테이블에 생기는 것**
- 위 표의 컬럼 약 12개 (암호화 컬럼은 `_ENC`, 해시는 `_HASH`)
- 휴대폰 해시의 키 버전 (`HASH_KEY_VER`, 회원 C-25와 같은 방식)
