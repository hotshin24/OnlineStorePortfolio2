## 10-5. 조회 패턴별 인덱스

**무엇을 정하나요?**
주문 테이블에 **어떤 인덱스를 처음부터 만들어 둘지**입니다.

**인덱스란?**
책 뒤의 찾아보기처럼, 특정 컬럼 값으로 행을 빨리 찾게 해 주는 구조입니다.
- 많을수록 조회는 빨라집니다.
- 대신 주문을 저장할 때마다 인덱스도 함께 고쳐야 해 쓰기가 느려집니다.
- 그래서 실제로 쓰는 조회만 골라 만듭니다.

**지금까지 정한 패턴에서 나온 조회**

| 조회 | 인덱스 후보 | 관련 패턴 |
|---|---|---|
| 회원의 주문 목록 (최근순) | 주문 (회원 ID, 주문 일시) | |
| 관리자 주문 검색 | 주문 (주문 상태, 주문 일시) | 7-1 |
| 비회원 주문 조회 | 주문번호 UK (이미 있음) | 3-2 |
| 결제 만료 배치 | 주문 (주문 상태, 결제 만료 일시) | 3-4 |
| 공급 기한 감시 | 주문 상품 (주문 상품 상태, 공급 조치 기한) | 8-4 |
| 자동 구매 확정 배치 | 주문 상품 (주문 상품 상태, 배송 완료 일시) | 7-5 |
| 재판매 의심 검사 | 주문 (배송 주소 해시), 주문 (주문자 휴대폰 해시) | 8-3 |
| 비회원 주문 회원 연결 | 주문 (주문자 휴대폰 해시): 위와 같은 인덱스 | 9-2 |
| 개인정보 파기 배치 | 주문 (개인정보 보유 종료일) | 10-1 |
| 장바구니 정리 배치 | 장바구니 (수정 일시) | 2-4 |

FK 컬럼(주문 상품의 주문 ID 등)은 이미 있는 UK의 첫 컬럼이면 따로 만들지 않습니다. 예를 들어 4-2 A의 UK(주문 ID, SKU ID)가 주문 ID 조회를 함께 처리합니다.

**선택지**

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 위 표의 조회만 복합 인덱스로 만듦. FK는 UK 첫 컬럼으로 처리되지 않는 것만 따로 만듦. 새 조회가 생기면 그때 더함 | 쓰기 부담이 최소. 각 인덱스가 왜 있는지 설명할 수 있음 | 표에 없는 조회는 처음에 느릴 수 있음 |
| B | FK마다 단일 인덱스만 만듦 | 규칙이 단순함 | 회원 주문 목록처럼 두 컬럼으로 찾는 조회가 느림. 배치용 조회를 처리하지 못함 |
| C | 자주 쓸 것 같은 컬럼마다 넉넉히 만듦 | 조회 걱정이 적음 | 주문 저장이 느려짐. 발매처럼 몰릴 때 병목이 됨 |

**추천: A.**
- 상품 도메인 PC-12 B와 같은 방침입니다.
- 파티션(10-3 A)과 함께 쓸 때는 다음과 같이 나눕니다.
  - **주문 일시가 들어간 인덱스:** 파티션별 인덱스(LOCAL)로 만듦. 오래된 달을 지울 때 인덱스도 함께 정리됨
  - **주문번호 UK와 해시 인덱스:** 기간과 상관없이 찾으므로 전체 인덱스(GLOBAL)로 만듦

**A를 고르면 생기는 것**
- 인덱스 약 9개 (표 기준, 중복 제거)
- 이름은 선행 3 형식 `IX_{테이블}_{컬럼}`

**사용자:** a

10-5는 A로 메모했습니다.
