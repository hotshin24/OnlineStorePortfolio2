## 7-4. 상태 전이 규칙 위치

**무엇을 정하나요?**
"어떤 상태에서 어떤 상태로 바꿀 수 있는지" 규칙을 **DB에 데이터로 둘지, 애플리케이션 코드에 둘지**입니다.

**전이 규칙이란?**
- 결제 대기 → 결제 완료: 가능
- 결제 대기 → 결제 만료: 가능
- 배송 완료 → 결제 대기: 불가능
- 구매 확정 → 출고: 불가능

이 규칙을 어기는 변경이 들어오면 막아야 합니다.

**예시로 보면**
배포한 코드에 버그가 있어, 이미 구매 확정된 상품이 택배사 지연 알림 때문에 "배송 중"으로 되돌아갔습니다. 구매 확정이 풀린 것처럼 보이고, 적립금 확정이 꼬입니다.

**선택지**

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | 허용 전이 표를 DB에 둠 (공통코드의 상태 값마다 `ATTR`에 다음으로 갈 수 있는 상태 목록을 적음). 애플리케이션이 이 표를 읽어 검사함 | 규칙이 DB 문서와 함께 보임. 관리자 화면에서 규칙을 확인할 수 있음 | 규칙을 바꾸면 결국 코드도 함께 바꿔야 함 (전이마다 따르는 처리가 있음). 두 곳을 맞춰야 함 |
| **B** | 전이 규칙은 애플리케이션 코드에 둠. 이력(7-3 C)에 이전·다음 상태가 남으므로, 6-10 A의 매일 검증 배치에 "허용되지 않은 전이" 검사 SQL을 더함 | 규칙과 처리가 한 곳(코드)에 있음. 위반이 생기면 하루 안에 찾음 | DB만 보고는 규칙을 알 수 없음 (설계 문서에 표로 적어 둠) |
| C | 트리거로 위반을 막음 | 위반이 저장되지 않음 | 트리거를 쓰지 않는 방침(1-6 A, 6-10 A)과 맞지 않음 |

**추천: B.**
- 상태가 바뀔 때는 재고 해제, 적립금 확정, 알림 발송 같은 처리가 함께 일어납니다. 그래서 "어디로 갈 수 있나"만 DB에 두어도 실제 동작은 코드가 정합니다. 규칙을 두 곳에 나누면 어긋날 곳만 늘어납니다.
- 이력에 이전·다음 상태가 남으므로(7-3 C), DB는 사후 검증으로 지킵니다. 이것은 6-10 A의 검증 배치에 SQL 하나를 더하는 것입니다.
- 전이 표는 설계 문서(컬럼 정의서의 코드 값 설명)에 적어 둡니다.

**B를 고르면 생기는 것**
- 새 테이블이나 컬럼은 없습니다.
- 검증 SQL 1개 추가 (허용 전이 목록에 없는 이력 행 찾기)
- 상태 코드 값 설명에 "다음으로 갈 수 있는 상태"를 문서로 적음
