5~7 분야(15개)를 설명합니다. 회원 도메인을 다시 확인하다가 주문에서 처리할 것이 하나 더 있어서 **5-7 임직원 할인 한도 사용 기록**을 추가했습니다. 그래서 전체 패턴은 45개가 됐습니다. 8~10 분야는 다음에 이어서 쓰겠습니다.

## 5. 금액·할인

### 5-1. 금액 컬럼 구성

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 주문 상품에 단가, 수량, 상품 금액, 할인 합계, 결제 대상 금액을 둠. 주문 헤더에는 그 합계 캐시(상품 금액, 출처별 할인 합계, 배송비, 최종 결제 금액)를 둠. 둘 다 주문 시점 값이고 바꾸지 않음. 취소·반품으로 줄어든 금액은 클레임에 남김 | 목록과 영수증은 헤더만 읽음. 부분 반품 환불은 주문 상품 단위로 계산 | 헤더 캐시와 행 합계가 맞는지 검증 필요 (5-6) |
| B | 주문 상품에만 금액을 두고 헤더는 매번 합산 | 중복 없음 | 주문 목록마다 집계 조회가 필요 |
| C | 헤더에만 금액을 둠 | 단순 | 부분 취소·반품 환불액을 계산할 근거가 없음 |

**추천: A.**

### 5-2. 할인 배분 방식과 끝전
주문 상품 × 할인 출처 배분 테이블(`ORD_ORDER_ITEM_DISCOUNT`)을 두는 것은 확정입니다 [선행 15]. 여기서 정할 것은 나누는 방법입니다.
- 상품 쿠폰은 해당 상품에만 붙습니다.
- 장바구니 쿠폰이나 주문 쿠폰처럼 주문 전체에 걸린 할인은 여러 주문 상품에 나눠야 합니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 대상 주문 상품의 결제 대상 금액에 비례해 1원 단위로 나누고, 끝전은 금액이 가장 큰 주문 상품에 더함. 할인·적립 적용 제외 상품(상품 결정 31)은 배분 대상에서 뺌 | 부분 반품 때 환불할 할인액이 행마다 정해져 있음. 끝전이 한 행에만 몰려 검증이 쉬움 | 배분 규칙을 구현해야 함 |
| B | 수량에 비례해 나눔 | 계산이 단순 | 비싼 상품과 싼 상품이 같은 할인을 받아, 싼 상품을 반품하면 할인을 과하게 돌려받음 |
| C | 비례 배분하고 끝전은 마지막 행에 더함 | 단순 | 마지막 행이 작은 금액이면 할인이 상품 금액보다 커질 수 있음 |

**추천: A.**

### 5-3. 배송비 위치

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 주문 헤더에 기본 배송비, 도서산간 추가 배송비, 배송비 할인(무료 배송 쿠폰)을 둠. 부분 반품 때 무료 배송 조건이 깨지면 배송비를 다시 계산하는 것은 클레임 도메인이 함 | 주문당 배송지 1개(3-4 A)와 맞음. 영수증과 같음 | 주문 상품별 배송비는 따로 계산 |
| B | 배송비를 주문 상품에 나눔 | 부분 환불이 단순 | 실제로 상품마다 배송비를 매기지 않아 배분 근거가 인위적 |
| C | 배송비를 배송 도메인의 출고 단위에 둠 | 나눠 보낼 때 정확 | 출고는 주문 뒤에 정해져, 주문 시점 결제 금액을 확정할 수 없음 |

**추천: A.**

### 5-4. 적립금·예치금 사용액 배분
적립금과 예치금은 원장과 건별 차감 기록을 두는 것이 확정입니다 [선행 15]. 여기서 정할 것은 주문에서 쓴 금액을 주문 상품에 나눌지입니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 할인 배분 테이블에 출처 유형(쿠폰, 적립금, 예치금, 임직원 할인 등)을 두고 같은 방식(5-2 A)으로 나눔 | 부분 반품 때 돌려줄 적립금과 예치금이 행마다 정해져 있음. 배분 규칙이 하나 | 적립금·예치금을 회계상 할인으로 볼지 결제 수단으로 볼지는 정산 도메인에서 따로 다룸 |
| B | 헤더에 사용액만 두고, 반품 때 비율로 계산 | 저장이 적음 | 여러 번 부분 반품하면 끝전이 어긋남 |
| C | 적립금·예치금용 배분 테이블을 따로 둠 | 할인과 분리 | 같은 구조의 테이블이 하나 더 생김 |

**추천: A.**

### 5-5. 적립 예정 금액
적립금 원장의 상태가 예정·확정·취소인 것은 확정입니다 [선행 15]. 구매 확정 때 등급 적립률(`MBR_GRADE.POINT_ACCUMULATION_RT`)로 적립합니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 주문 상품마다 적립금 원장에 "예정" 행을 만들고, 주문에는 두지 않음. 주문 화면은 원장을 조회 | 적립의 원천이 원장 하나. 부분 반품 때 그 행만 취소 | 주문 상세에서 원장을 조회 |
| B | A + 주문 상품에 적립 예정 금액 캐시 | 주문 화면에서 바로 보임 | 원장과 같은 값을 두 번 저장 |
| C | 헤더에 합계만 두고 원장은 구매 확정 때 만듦 | 단순 | 부분 반품 때 적립 금액을 다시 계산해야 함 |

**추천: A.** 적립률은 주문 시점 값이어야 합니다. 그래서 예정 행을 주문 때 만들어야 등급이 바뀌어도 금액이 흔들리지 않습니다.

### 5-6. 금액 정합성 검증

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 행 안에서 계산되는 식은 CHECK로 검사함 (상품 금액 = 단가 × 수량, 결제 대상 금액 = 상품 금액 − 할인 합계 ≥ 0). 행 사이 합계(헤더 = 주문 상품 합계, 할인 합계 = 배분 합계)는 애플리케이션이 저장 때 검사하고 매일 검증 배치가 다시 확인함 | DB가 막을 수 있는 것은 DB가 막음. 대량 저장이 느려지지 않음 | 행 사이 오류는 배치가 잡을 때까지 남을 수 있음 |
| B | 트리거로 헤더 합계를 강제 | DB가 모두 보장 | 주문 상품을 저장할 때마다 트리거가 돎. 행사일 대량 주문에서 잠금 경합 |
| C | 애플리케이션 검사만 | 단순 | 근거 기록이 없음 |

**추천: A.**

### 5-7. 임직원 할인 한도 사용 기록 (추가)
회원 도메인의 `MBR_EMPLOYEE_ANNUAL_DISCOUNT_LIMIT.USED_DISCOUNT_AMT` 설명은 이렇습니다: "주문 때 더하고 취소·반품 때 뺀다. 상세 근거는 주문 상품 할인 배분 테이블(15-5)."

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 임직원 할인을 할인 배분 테이블의 출처 유형 하나로 기록함. 주문을 만들 때 그 회원의 해당 연도 한도 행을 잠그고 남은 한도를 확인한 뒤 사용액을 더함. 클레임 환불 때 배분 행 기준으로 뺌 | 회원 도메인의 기존 결정과 그대로 맞음. 동시 주문으로 한도를 넘는 것을 막음 | 한도 행 잠금이 한 회원 안에서만 걸림 (영향 작음) |
| B | 사용액 캐시 없이 매번 배분 테이블을 합산 | 캐시 불일치 없음 | 회원 도메인이 이미 사용액 컬럼을 두기로 함 |
| C | 연도는 주문일이 아니라 결제일 기준 | 결제 대기 중 해가 바뀌는 경우를 정확히 처리 | 예외가 드묾. 기준 일자를 하나 더 정해야 함 |

**추천: A.** 연도 기준은 주문 생성 일시로 합니다.

## 6. 장바구니
장바구니에 회원 ID와 비회원 장바구니 키 중 정확히 하나를 두고 CHECK를 거는 것은 확정입니다 [선행 14]. 회원 소유 목록이라 물리 삭제합니다 [선행 4].

### 6-1. 장바구니 행 단위

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | SKU당 1행 + 수량. UK(회원 ID, 비회원 키, SKU ID). 같은 SKU를 다시 담으면 수량을 더함. 1회 주문 한도(`PER_ORDER_LIMIT_QTY`)는 담을 때 안내만 하고 주문 때 검사 | 중복 행 없음. 주문 상품 행 단위(2-2 A)와 같음 | 같은 SKU를 다른 추가 옵션으로 담으려면 8-4 결정에 따라 UK를 바꿔야 함 |
| B | 담을 때마다 행 추가 | 단순 | 같은 상품이 여러 줄로 보임 |
| C | 스타일·컬러 단위로 담고 사이즈는 나중에 고름 | 사이즈 미정으로 담기 가능 | 주문 전에 반드시 SKU로 바꿔야 함. 재고 확인 불가 |

**추천: A.** UK에 NULL 컬럼이 있어도 Oracle 복합 UK는 NULL이 아닌 값이 같은 행을 막습니다. 그래서 회원과 비회원 각각 중복이 막힙니다.

### 6-2. 비회원 장바구니 병합

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 로그인하면 비회원 키의 행을 회원 행으로 옮기고, 같은 SKU는 수량을 더함 (1회 주문 한도를 넘으면 한도까지만) | 담아 둔 상품을 잃지 않음 | 병합 규칙 1개 |
| B | 회원 장바구니만 남기고 비회원 행은 버림 | 단순 | 로그인 직전에 담은 상품이 사라짐 |
| C | 병합할지 고객에게 물음 | 고객이 선택 | 화면 단계가 늘어남. DB는 A와 같음 |

**추천: A.**

### 6-3. 담을 때 가격 저장

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | 저장하지 않음. 항상 현재 가격을 보여 줌 | 컬럼 없음 | "담은 뒤 가격이 내렸어요" 안내를 할 수 없음 |
| **B** | 담을 때 판매가(컬러 판매가 + SKU 추가 금액)를 저장함. 표시용으로만 쓰고 주문 가격은 항상 현재 가격 | 가격 변동 안내의 근거. 컬럼 1개 | 표시용 값임을 설명에 분명히 해야 함 |
| C | 담을 때의 가격 이력 행 ID를 저장 | 어떤 가격이었는지 정확 | FK가 늘어남. 안내에는 금액만 있으면 됨 |

**추천: B.**

### 6-4. 보관 기간
행마다 기한이 다른 테이블이라 대량 삭제는 나눠서 DELETE합니다 [선행 11].

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 마지막으로 수정한 날부터 회원 90일, 비회원 30일이 지나면 배치로 물리 삭제 | 비회원 행이 무한히 쌓이지 않음 | 기간은 정책값으로 정해야 함 |
| B | 회원은 무기한, 비회원은 30일 | 회원 편의 | 회원 행이 계속 쌓임 |
| C | 모두 30일 | 단순 | 회원이 오래 담아 둔 상품이 사라짐 |

**추천: A.** 기간 값은 공통코드 정책값에 둡니다.

## 7. 주문 생성 정합성

### 7-1. 중복 주문 방지
중복 요청 키를 DB에 두는 것은 확정입니다 [선행 9]. PG 거래는 (대행사 코드 + 거래번호) UK로 막습니다 [선행 13, 결제 도메인].

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 주문 행에 주문 요청 키 컬럼(주문서 화면이 발급하는 무작위 값)을 두고 UK를 검 | 버튼을 두 번 눌러도 주문이 하나. 테이블 없음 | 키 발급은 화면이 맡음 |
| B | 모든 도메인이 함께 쓰는 중복 요청 키 테이블(SYS)을 둠 | 결제, 클레임에도 같은 방식 | 테이블 1개. 정리 배치가 필요. 주문은 A로도 충분 |
| C | 같은 회원이 최근 몇 초 안에 같은 상품을 주문했는지 검사 | 컬럼 없음 | 정상적인 재주문을 막을 수 있음. 동시 요청은 못 막음 |

**추천: A.**

### 7-2. 재고 확보 시점
재고 수량과 원장은 재고 도메인(INV)이 맡습니다. 주문 도메인은 언제 재고를 잡아 달라고 요청할지만 정합니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 결제 대기 주문을 만들 때 가용 재고를 할당함. 결제 대기가 만료되거나 취소되면 복구 | 한정 수량과 발매 상품의 초과 판매를 막음 | 결제하지 않은 주문이 잠시 재고를 잡음 (7-4 만료 시간으로 제한) |
| B | 결제 승인 때 할당 | 잡아 두는 재고가 없음 | 결제 중에 품절되면 승인을 취소해야 함 |
| C | 출고 때 차감 | 단순 | 초과 판매가 일상적으로 생김 |

**추천: A.** 예약 판매 SKU는 재고 대신 "입고 예정 수량 − 예약 주문 수량"을 할당합니다 (상품 PC-41 C).

### 7-3. 구매 수량 제한 검사
상품에 한도 세 가지가 있습니다.
- 1회 주문 한도 `PER_ORDER_LIMIT_QTY`
- 1인 1일 한도 `DAILY_LIMIT_QTY`: 설명에 "검사는 주문 도메인"이라고 되어 있습니다.
- 1인 누적 한도 `PER_MEMBER_TOTAL_LIMIT_QTY`: 회원 전용입니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 주문을 만들 때 그 회원의 유효 주문 상품 수량(취소·결제 전 만료 제외)을 스타일별로 합산해 검사함. 같은 회원·스타일 동시 주문은 회원 단위 잠금으로 막음. 비회원의 1일 한도는 주문자 휴대폰 해시로 셈 | 집계 테이블 없음. 인덱스(회원, 스타일, 주문일)로 충분 | 검사 쿼리 1개. 행사 상품 주문이 몰리면 회원 잠금이 필요 |
| B | 회원 × 스타일 누적 구매 수량 집계 테이블을 둠 | 검사가 빠름 | 테이블 1개. 취소·반품 때 집계를 되돌려야 함 |
| C | 애플리케이션 검사만 (잠금 없음) | 단순 | 동시 주문으로 한도를 넘을 수 있음 |

**추천: A.**

### 7-4. 결제 대기 주문 만료
1-2 A를 고르면 결제하지 않은 주문이 생깁니다. 결제 전이라 돌려줄 돈이 없으므로 클레임이 아니라 주문 상태로 끝냅니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 주문 행에 결제 기한 일시를 둠 (결제 수단별: 카드 등은 짧게, 가상계좌는 입금 기한). 배치가 기한이 지난 주문을 "결제 전 취소"로 바꾸고 재고 할당·쿠폰 선점·적립금 사용을 되돌림 | 수단마다 다른 기한을 표현. 잡아 둔 재고가 빨리 풀림 | 컬럼 1개, 배치 1개 |
| B | 생성 후 일정 시간 일괄 만료 | 단순 | 가상계좌 입금 기한을 표현할 수 없음 |
| C | 만료 없음 | 없음 | 재고와 쿠폰이 계속 잡혀 있음 |

**추천: A.** 결제 수단별 기한 값은 공통코드 정책값에 둡니다.
