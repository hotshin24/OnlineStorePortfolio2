## 1. 범위·경계

### 1-1. 주문 도메인이 맡는 범위
주문은 결제(PAY), 클레임(CLM), 배송(DLV), 재고(INV), 프로모션(PRM)과 맞닿아 있습니다. 어디까지를 주문 테이블에 둘지 먼저 정해야 나머지 패턴의 범위가 정해집니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 주문(ORD)은 장바구니, 주문, 주문 상품, 할인 배분, 주문 상태 이력, 배송지 스냅샷까지. 결제·취소·반품·교환·출고·송장·재고는 각 도메인이 맡고, 주문 상품 ID를 FK로 받음 | 도메인마다 책임이 하나. 선행 결정의 접두어 분리(PAY, CLM, DLV)와 같음 | 화면 하나(주문 상세)가 여러 도메인을 조회함 |
| B | A + 취소(출고 전)는 주문 상태로 처리하고, 반품·교환만 클레임 | 단순 취소가 가벼움 | 부분 취소, 환불, 재고 복구 규칙이 두 도메인으로 갈림 |
| C | 주문이 출고 단위(배송 그룹)까지 맡고, 배송은 송장·추적만 | 출고 분리를 주문에서 바로 봄 | 출고는 창고 작업(WMS) 결과라 주문 시점에 확정할 수 없음 |

**추천: A.** 취소도 환불과 재고 복구가 따라오는 클레임입니다. 한 곳(CLM)에서 처리해야 부분 취소와 반품의 규칙이 갈리지 않습니다.

### 1-2. 주문 행을 만드는 시점

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 결제 요청 직전에 "결제 대기" 상태로 주문을 만들고, 결제가 승인되면 "결제 완료"로 바꿈 | PG에 넘길 주문번호가 미리 있음. 가상계좌 입금 대기, PG 콜백 지연, 결제 중 이탈을 모두 표현할 수 있음 | 결제하지 않은 주문이 쌓여 만료 처리가 필요함 (7-4) |
| B | 결제 승인 뒤에 주문을 만듦 | 결제된 주문만 있음 | 가상계좌처럼 입금을 기다리는 결제를 표현할 수 없음. 승인됐는데 주문 생성이 실패하면 고아 결제가 생김 |
| C | 결제 전에는 임시 주문서 테이블에 두고, 승인되면 주문으로 옮김 | 주문 테이블이 깨끗함 | 같은 데이터를 두 번 저장하고 옮기는 테이블이 하나 늘어남 (규칙 5 테이블 최소화와 맞지 않음) |

**추천: A.** 복수 PG와 간편결제를 직접 계약했으므로(선행 13) 결제 흐름의 모든 중간 상태를 주문 행으로 남기는 편이 안전합니다.

### 1-3. 주문서(체크아웃) 임시 데이터
주문서 화면에서 고르는 쿠폰, 적립금, 배송지를 결제 요청 전까지 어디에 둘지에 대한 패턴입니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | DB에 두지 않음 (화면 상태). 결제 요청 때 1-2 A의 결제 대기 주문을 만들면서 검증하고 저장 | 테이블 없음 | 주문서를 새로 고치면 선택이 사라짐 |
| B | 체크아웃 세션 테이블에 계산 결과와 쿠폰 선점을 저장하고 만료 시각을 둠 | 쿠폰 선점과 재진입을 지원함 | 테이블 1개와 만료 배치. 결제 대기 주문과 역할이 겹침 |
| C | 장바구니 행에 "주문서 선택" 표시만 둠 | 컬럼 하나 | 쿠폰과 적립금은 담을 곳이 없음 |

**추천: A.** 쿠폰 선점은 결제 대기 주문이 생길 때 하면 충분합니다.

## 2. 주문 구조

### 2-1. 주문 계층

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 주문 → 주문 상품 2단. 나눠 출고하는 단위는 배송 도메인의 출고·송장이 주문 상품을 묶음 | 단순. 예약 상품과 일반 상품을 나눠 보내는 경우도 배송 쪽에서 표현 | 배송비를 출고 단위로 나누려면 배송 쪽 규칙이 필요 |
| B | 주문 → 배송 그룹 → 주문 상품 3단 (배송 그룹 = 배송지·배송비·출고 예정 단위) | 다중 배송지와 묶음별 배송비를 주문 시점에 표현 | 테이블 1개. 배송지가 하나뿐이면 (3-4 A) 대부분 1:1 |
| C | 주문 → 주문 상품 → 수량 단위 행 3단 | 수량별 상태 추적 | 행이 수량만큼 늘어남. 2-2와 겹침 |

**추천: A.** 3-4에서 배송지를 하나로 정하면 배송 그룹은 주문과 거의 1:1입니다. 그러면 규칙 5(테이블 최소화)에 맞지 않습니다.

### 2-2. 주문 상품 행 단위

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | SKU당 1행 + 수량. 부분 취소·반품은 클레임 수량으로 기록하고, 주문 상품에는 취소·반품 수량 캐시를 둠 | 행 수가 최소. 리뷰 "주문 상품 1건당 1개"(선행 17)와 맞음 | 같은 SKU 3개 중 1개만 반품하면 수량 계산이 필요 |
| B | 수량 1개당 1행 | 부분 처리가 단순 | 같은 SKU 3개면 리뷰 대상이 3건이 되어 선행 17과 충돌. 행 수 증가 |
| C | SKU당 1행으로 시작하고, 부분 처리 때 행을 나눔 | 처리 뒤에는 행 단위 상태 | 행 분할로 원래 주문 내용을 추적하기 어려움. 할인 배분(선행 15)도 다시 나눠야 함 |

**추천: A.**

### 2-3. 주문번호 체계
주문번호는 업무 키(`ORDER_NO`, UK)이고 재사용 금지 값입니다 [확정, 선행 4].

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | 날짜 + 일련번호 (예: `20261124` + 7자리 순번) | 읽기 쉽고 정렬 순서가 시간 순서 | 일별 주문량이 외부에 드러남. 비회원 조회 번호를 추측하기 쉬움 |
| **B** | 날짜 + 무작위 영숫자 (예: `20261124-K7Q2M9XA`) | 주문량을 숨기고 추측이 어려움. 날짜로 고객 문의를 바로 찾음 | 생성할 때 UK 충돌을 다시 시도해야 함 |
| C | 시퀀스 값 그대로 | 가장 단순 | 주문량 노출과 추측 문제가 가장 큼 |

**추천: B.** 비회원은 주문번호와 비밀번호로 조회하므로(선행 14) 번호를 추측하기 어려워야 합니다.

### 2-4. 주문 상품 식별 방식

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 대리 PK + 주문 안 순번 `ORDER_ITEM_SN` (UK: 주문 ID + 순번). 화면에는 "주문번호-순번"으로 표시 | 별도 번호를 발번하지 않음 | 외부(택배, CS)에서 단독 번호로 부를 수 없음 |
| B | 주문 상품 업무 키 `ORDER_ITEM_NO` (UK) | 단독 번호로 부를 수 있음 | 발번 규칙이 하나 늘어남 |
| C | 대리 PK만 | 가장 단순 | 화면과 문의에 내부 ID가 노출됨 |

**추천: A.**

## 3. 스냅샷

### 3-1. 상품 스냅샷 범위
주문 뒤에 상품이 바뀌어도 주문 내용이 남아야 합니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 핵심 컬럼만 복사: 품번, 상품명, 컬러명, 사이즈명, SKU 코드, 대표 이미지 경로. 상세 표시 내용은 상품의 표시 내용 이력(`PRD_DISPLAY_CONTENT_HIST`, 상품 결정 44) ID로 참조 | 주문 화면에 필요한 것만 복사. 계약 당시 표시 내용은 이력에서 찾음 | 표시 내용 이력 보관 기간을 주문 보관과 맞춰야 함 |
| B | A + 상품정보제공고시 전체를 JSON으로 복사 | 주문 행만으로 완결 | 주문 상품마다 큰 JSON. 같은 내용이 수십만 번 중복됨 |
| C | FK만 두고 현재 상품을 조회 | 저장 최소 | 상품이 바뀌면 과거 주문 내용이 달라짐 |

**추천: A.**

### 3-2. 가격 스냅샷과 가격 이력 참조
상품 도메인 PC-33에서 "가격 이력 행을 주문 스냅샷에 남길지는 주문 도메인에서 정한다"고 넘겼습니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | 금액 3개(정가, 판매가, SKU 추가 금액)와 이력 ID 3개(정가 행, 판매가 행, SKU 행)를 모두 저장 | 어느 행에서 왔는지 완전히 추적 | FK 3개. 정가·SKU 행은 시점 조회로도 찾을 수 있음 |
| B | 금액만 저장 | 단순 | 마크다운 차수, 컬러 특가 여부를 알려면 시점 조회가 필요 |
| **C** | 금액 3개 + 판매가 행 ID 1개 | 할인 근거(컬러 특가, 마크다운 차수)가 바로 보임. 반영 지연 중 주문의 가격 검증 | FK 1개 |

**추천: C.** 정가와 SKU 추가 금액은 바뀌는 일이 드물고, 실제 반영 시각 기준의 시점 조회(PC-67)로 찾을 수 있습니다.

### 3-3. 주문자·수령인 스냅샷
암호화 범위는 이미 정해져 있습니다 [확정, 선행 5와 회원 C-72]. 이름, 도로명·지번 주소는 평문 + TDE이고, 휴대폰, 이메일, 상세 주소는 암호화합니다. 주문자 휴대폰은 HMAC 해시를 둡니다 [확정, 선행 14]. 여기서 정할 것은 무엇을 어디에 복사하느냐입니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 회원·비회원 모두 주문 행에 주문자(이름, 휴대폰, 이메일)와 수령인(이름, 휴대폰, 주소)을 복사 | 회원 정보가 바뀌거나 탈퇴해도 주문이 완결됨. 회원과 비회원이 같은 구조 | 주문 행 컬럼이 많아짐 |
| B | 회원 주문은 회원 FK만 두고, 비회원만 복사 | 컬럼 중복이 적음 | 회원이 휴대폰을 바꾸면 과거 주문의 연락처가 달라짐. 탈퇴하면 주문 정보를 잃음 |
| C | 연락처를 1:1 별도 테이블로 분리 | 파기 단위가 분리됨 | 규칙 5 예외가 필요. 7번 공통 컬럼(행 단위 파기)으로도 같은 효과를 냄 |

**추천: A.**

### 3-4. 배송지 단위

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 주문당 배송지 1개 (주문 행 컬럼) | 단순. 국내 자사몰에서 가장 흔함 | 여러 곳으로 보내려면 주문을 나눠야 함 |
| B | 주문 상품별 배송지 (배송지 테이블 1:N) | 다중 배송 | 테이블 1개. 배송비와 출고 규칙이 복잡해짐 |
| C | A + 선물 수령인만 따로 | 선물하기 지원 | 8-5 선물하기 결정에 따라 달라짐 |

**추천: A.** 선물하기는 8-5에서 따로 다룹니다.

### 3-5. 공동현관 출입 방법 파기 시점
회원 C-71에서 넘어온 과제입니다. 회원 배송지의 `ENTRANCE_ACCESS_ENC`를 주문 배송지에 복사하면, 주문 보관(5년) 동안 출입 비밀번호가 남습니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 주문 상품이 모두 구매 확정되거나 반품 기간이 끝나면 NULL로 바꿈. 반품 회수 때까지는 남김 | 필요한 기간에만 보관. 최소 보유 원칙 | 파기 배치 조건 1개 |
| B | 주문 보관 기간(5년) 동안 유지 | 규칙 없음 | 출입 비밀번호를 필요 이상 보관함 |
| C | 주문에 복사하지 않고 출고 때 회원 배송지를 참조 | 복사 없음 | 비회원은 회원 배송지가 없음. 회원이 배송지를 고치면 이미 나간 주문과 달라짐 |

**추천: A.**

## 4. 상태

### 4-1. 상태를 두는 단위

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 주문 상품에 상태를 두고, 주문 헤더에는 대표 상태 캐시를 둠 (예: 일부 배송 중) | 부분 출고, 예약 상품의 늦은 출고, 부분 취소를 표현함 | 헤더 캐시 갱신 규칙이 필요 |
| B | 주문 헤더에만 상태 | 단순 | 예약 상품과 일반 상품이 섞인 주문을 표현할 수 없음 |
| C | 헤더와 주문 상품이 각자 상태를 가짐 | 각각 자유 | 둘이 어긋날 수 있음 |

**추천: A.**

### 4-2. 주문 상태와 클레임·배송 상태의 분리

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 주문 상품 상태는 주문 진행만 둠 (결제 대기 → 결제 완료 → 상품 준비 → 배송 중 → 배송 완료 → 구매 확정, 그리고 끝 상태 취소 완료·반품 완료). 클레임 진행 단계는 클레임 도메인 상태로 두고, 주문 상품에는 진행 중 클레임 여부와 취소·반품 수량만 둠 | 상태 코드가 작고 도메인마다 상태가 하나 | 주문 화면에서 클레임 단계를 보려면 클레임을 조회함 |
| B | 한 상태 코드에 클레임 단계까지 모두 넣음 (취소 요청, 반품 회수 중, 교환 재발송 등) | 한 컬럼으로 모두 보임 | 코드가 30개 이상으로 늘어남. 부분 수량 클레임을 표현할 수 없음 |
| C | 결제 상태, 배송 상태, 클레임 상태 컬럼을 주문 상품에 따로 둠 | 측면별로 보임 | 다른 도메인의 상태를 복사한 것이라 어긋날 수 있음 |

**추천: A.**

### 4-3. 상태 이력 단위
대량 도메인인 주문은 전용 상태 이력 테이블을 둡니다 [확정, 선행 6]. 여기서 정할 것은 이력을 남기는 단위입니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 주문 상품 단위 이력 1개 (`ORD_ORDER_ITEM_STATUS_HIST`). 헤더 대표 상태는 캐시라 이력을 두지 않음 | 상태의 원천과 이력 단위가 같음 | 주문 전체 흐름은 주문 상품 이력을 모아서 봄 |
| B | 주문 단위 이력과 주문 상품 단위 이력 2개 | 둘 다 바로 보임 | 테이블 1개 추가. 캐시 이력은 중복 |
| C | 주문 단위만 | 테이블 1개 | 부분 출고와 부분 취소를 남기지 못함 |

**추천: A.** 선행 결정 문서의 후보 이름은 `ORD_ORDER_STATUS_HIST`였습니다. 단위를 정하면 이름도 함께 정합니다.

### 4-4. 상태 전이 통제
상태 코드에는 CHECK를 겁니다 [확정, 규칙 4].

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 값 CHECK + 허용 전이표를 공통코드 속성(`ATTR`)에 두고 애플리케이션이 검사. 이력 행에 이전 상태와 다음 상태를 남김 | 전이 규칙이 데이터로 보이고 바꾸기 쉬움 | DB가 잘못된 전이를 막지는 못함 |
| B | 전이 허용 테이블과 트리거로 DB가 강제 | DB가 막음 | 트리거 유지보수. 배치 대량 처리가 느려짐 |
| C | 애플리케이션 코드에만 둠 | 단순 | 규칙이 문서와 코드에 흩어짐 |

**추천: A.**
