## 6-10. 금액 정합성 검증

**무엇을 정하나요?**
여러 곳에 나눠 저장한 금액과 수량이 **서로 맞는지 어떻게 확인할지**입니다.

**왜 필요한가요?**
지금까지 고른 패턴 중 "같은 값을 두 곳에 둔" 것이 여럿 있습니다.

| 규칙 | 관련 패턴 |
|---|---|
| 주문 헤더 금액 = 주문 상품 금액 합계 (배송비 제외) | 6-1 A |
| 출처별 할인액 = 그 출처의 배분 행 합계 | 6-4 A, 6-5 A |
| 과세 금액 + 면세 금액 = 결제 금액 | 6-7 A |
| 성공한 결제 금액 합계 = 주문 결제 금액 | 1-2 A |
| 주문 상품의 취소·반품 수량 = 클레임 수량 합계 | 1-6 A |
| 임직원 사용 금액 = 임직원 할인 배분 합계 | 6-9 A |

이 중 한 행 안에서 확인할 수 있는 규칙(예: 과세 + 면세 = 결제)은 CHECK로 막습니다. 하지만 여러 행을 합해야 하는 규칙은 CHECK로 걸 수 없습니다.

**예시로 보면**
배포한 코드에 버그가 있어 할인 배분 합계가 쿠폰 할인액보다 1원 적게 저장되었습니다. 저장할 때는 아무도 모릅니다. 몇 달 뒤 부분 반품 환불액이 1원씩 틀려 정산이 맞지 않습니다.

**선택지**

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 한 행 안의 규칙은 CHECK로 막음. 여러 행 규칙은 매일 검증 SQL을 Oracle 스케줄러 배치로 돌려, 전날 바뀐 주문만 확인함. 불일치 건수는 배치 실행 이력(`BAT`)에 남기고 관리자에게 알림 | 버그를 하루 안에 찾음. 새 테이블이 없음. 확정된 배치 방침(선행 11: 집계는 Oracle 스케줄러)과 맞음 | 불일치가 생긴 뒤에 찾으므로 하루 동안은 틀린 값이 있을 수 있음 |
| B | A에 더해 불일치 건마다 행을 남기는 검증 결과 테이블을 둠 (주문 ID, 규칙, 기대값, 실제값, 조치 일시) | 어느 주문이 어떻게 틀렸고 언제 고쳤는지 추적함 | 테이블 1개. 정상이라면 거의 비어 있음 |
| C | 트리거로 저장할 때마다 확인함 | 틀린 값이 들어가지 않음 | 트리거를 쓰지 않는 방침(1-6 A)과 맞지 않음. 주문 저장이 무거워짐 |

**추천: A.**
- 저장할 때는 애플리케이션 공통 코드가 맞춰 넣고, 배치가 뒤에서 다시 확인하는 이중 구조입니다.
- 불일치는 드물어야 정상입니다. 드문 일을 위해 테이블을 두기보다, 배치 실행 이력에 건수를 남기고 알림으로 조치합니다. 어느 주문인지는 검증 SQL을 다시 돌리면 나옵니다.
- 결제 금액 대사(PG에서 실제로 들어온 돈과 맞추기)는 결제·정산 도메인의 외부 대사 배치(선행 11: 애플리케이션 배치)가 맡습니다. 여기서는 DB 안의 정합성만 다룹니다.

**A를 고르면 생기는 것**
- 새 테이블이나 컬럼은 없습니다.
- 검증 SQL 6개 (위 표). 배치 등록은 배치 도메인에서 정합니다.

**사용자:** a

6-10은 A로 메모했습니다. 6분야 10개를 모두 마쳤습니다.
