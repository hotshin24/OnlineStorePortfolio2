#title 고객 취소를 1차에 열지
#target 1차 범위 (6개 도메인 공통) · 외부 검토 2개
#what
결제를 마친 주문을 고객이 취소하는 기능을 1차에 넣을지 정합니다. 넣으면 환불 요청의 근거인 클레임 테이블을 먼저 설계해야 합니다(결제 1-3 A).

배경: 6개 도메인을 한꺼번에 확정하기에는 범위가 넓어, 코드로 처음 구현할 범위(1차)부터 컬럼을 확정하기로 했습니다(사용자 요청). 외부 검토 2개를 결정과 대조해 바로잡은 점은 이렇습니다.
- 클레임 도메인 없이 1차에 "출고 전 전체 취소"를 연다(첫째 검토): 결제 1-3 A와 맞지 않습니다. 환불 요청은 근거가 `CLAIM_ID`, `ORDER_CHANGE_HIST_ID`, 결제 자체 사유 중 정확히 하나여야 하고(CHECK), 결제 자체 사유는 금액 불일치 자동 취소, 이상 승인 자동 취소, 만료 뒤 입금 환불, 차지백, PG 관리자 화면 취소뿐입니다.
- 가입 때 본인인증은 1차에서 뺀다(첫째 검토): 가입 때 함께 만드는 `MBR_JOIN_ATTRIBUTION`의 `JOIN_AGE_GROUP_CD`가 NOT NULL이고 본인인증 생년월일로 채우며(대화에서는 `MBR_MEMBER`의 컬럼으로 잘못 말했고 1차-5에서 바로잡음), 1인 1계정(4-1)도 CI 해시로 확인하므로 뺄 수 없습니다. `MBR_IDENTITY_VERIFICATION_LOG`가 1차입니다.
- 재고 1차에 `INV_STOCK_COMMITMENT_EVENT`가 없다(첫째 검토): IC-10 B로 확보를 해제·출고할 때 같은 트랜잭션에서 남기므로 빠지면 안 됩니다.
- `SYS_IDEMPOTENCY_KEY`(첫째 검토): 정한 적이 없습니다. 중복 방지 키는 각 행에 있습니다(`ORDER_REQUEST_KEY_VAL`, `SHIPMENT_REQUEST_KEY_VAL`, `LEDGER_KEY_VAL`).
- 테이블 수(첫째 검토): 결론의 39개, 표의 42개, 상품 목록(10개라 적고 11개 나열)이 서로 맞지 않습니다.
- 기초 재고로 시작하면 입고 예정은 뒤 차수(둘째 검토): 맞습니다(IC-79 A). 다만 생산 입고를 1차에 열면 T-5 A로 입고 예정이 필수입니다.
#ex
**예시:** 고객이 니트 1벌(59,000원)을 결제했고, 출고 전에 취소하려 합니다. 이때 환불 요청의 근거가 될 클레임 ID가 있어야 PG 취소까지 갈 수 있습니다. 반면 결제 만료 뒤 늦게 도착한 승인 59,000원은 결제 자체 사유라서 클레임 없이 자동 취소됩니다.
#opt A
1차는 자동 취소만 엽니다(만료 뒤 승인, 금액 불일치). 고객 취소·반품·교환은 2차에 클레임 도메인과 함께 엽니다
미설계 도메인 없이 1차를 시작합니다. 환불 요청·취소 테이블 구조는 1차에 이미 검증됩니다
1차만으로는 실제로 오픈할 수 없습니다(청약철회 의무)
#opt B
클레임 최소 설계(출고 전 전체 취소)를 1차에 넣습니다
고객 취소까지 한 흐름으로 구현합니다
클레임 도메인의 패턴 검토와 결정을 1차 앞에 해야 합니다
#opt C
B에 반품·교환까지 넣습니다
운영 가능한 최소 형태입니다
회수 배송, 재고 복원, 부분 환불까지 1차가 커집니다
#rec A
#reason
1차는 "처음 구현해서 흐름을 검증하는 단위"이고, 클레임은 아직 패턴 검토도 하지 않았습니다. 환불 요청과 취소 테이블은 자동 취소로 1차에 이미 쓰이므로, 2차에는 클레임 ID만 연결하면 됩니다.
#choice A
#answer 1 a, 2 a, 3 a, 4 a,
#apply
진행메모 "1차 범위" 절과 CLAUDE.md 진행 상황에 적었다. 1차 흐름은 시스템 자동 취소까지이고, 고객 취소·반품·교환은 2차에 클레임 도메인과 함께 연다.

#opt B

#rec A
#reason

#choice A

#rec A
#reason

#title 1차 테이블의 컬럼을 어디까지 확정할지
#target 1차 범위 · 6개 도메인 정의서
#what
1차 테이블의 컬럼을 전부 확정할지, 나중에 바꾸기 비싼 것만 확정할지 정합니다.
#ex
**예시:** `ORD_ORDER`에서 적립금 사용액은 금액 합계 CHECK에 들어가므로 1차에 확정합니다. 반면 UTM 같은 NULL 허용 분석 컬럼은 뒤에 `ALTER TABLE … ADD`로 넣어도 기존 행에 영향이 없습니다.
#opt A
1차 흐름이 쓰는 컬럼과, 흐름과 상관없이 바꾸기 비싼 것(PK·UK·FK, 파티션 키, NOT NULL과 기본값, 상태 코드·전이, 여러 컬럼 CHECK, 암호화·해시 컬럼)을 확정합니다. 나머지 NULL 허용 컬럼은 그 업무를 여는 차수에 확정합니다
1차 검토량이 크게 줄어듭니다. 나중에 바꾸면 비싼 것은 놓치지 않습니다
테이블 하나의 확정이 여러 차수에 나뉩니다(정의서에 차수 표시가 필요)
#opt B
1차 테이블은 컬럼 전체를 확정합니다(지금 방식)
테이블 단위로 끝납니다
2차 기능 컬럼까지 1차에 검토해야 합니다
#rec A
#reason
6개 도메인의 1차 테이블이 약 40개라 전부 확정하면 1차가 끝나지 않습니다. Oracle에서 NULL 허용 컬럼을 더하는 것은 사전 정보만 바꾸므로 뒤로 미뤄도 비용이 거의 없습니다.
#choice A
#answer 1 a, 2 a, 3 a, 4 a,
#apply
1차 테이블 43개(회원 9, 상품 11, 주문 4, 결제 6, 재고 4, 배송 9)와 공통·관리자 최소 설계를 진행메모에 적었다. 차수 표기는 사용자 결정으로 정의서의 확정 칸 옆에 따로 두고(이어서 "1차 범위로 남겨주고, 차수 표기는 확정 칸 옆에 따로 하자"), 재고 테이블 이름·컬럼정의서에 먼저 넣었다.

#title 1차 테이블과 공통 목록을 보충할지
#target 1차 범위 (6개 도메인 공통) · 외부 검토 (커밋 514bd88 기준)
#what
둘째 검토가 지적한 6개 테이블을 1차에 더할지, 공통 목록에 `SYS_EXTERNAL_VENDOR`·`SYS_STATUS_HIST`를 적을지 정합니다. 아래 오류 정정도 함께 반영합니다.

외부 검토를 대조한 결과:
- 더하자는 6개 테이블은 모두 맞습니다. `MBR_JOIN_ATTRIBUTION`(가입 완료 때 같은 트랜잭션, C-21, `JOIN_AGE_GROUP_CD` NOT NULL), `PAY_CARD_MERCHANT_CONTRACT`(승인이면 `SETTLEMENT_METHOD_CD` NOT NULL, PYC-74 A, 카드는 이 테이블에서 복사), `PAY_PG_CODE_MAPPING`(카드사 코드 변환 PYC-2 B, 실패 코드 판단 PYC-37 A), `INV_SAFETY_STOCK_HIST`(새 현재고 행의 신규 행 기본값 이력), `INV_MONTHLY_CLOSING`(원장 업무 일자는 열린 달만, 8-2 C), `DLV_COURIER_RATE`(운송장의 운임표 FK와 운임은 포장 때 모두 채우는 CHECK).
- 예약 조건(`GENERAL_ORDERABLE_QTY >= :수량`)과 원장 단위(`SHIP:{출고 ID}:{현재고 ID}`)는 정의서에 이미 그렇게 적혀 있습니다. 기초 재고 원장 CHECK는 수불 원장 검토 Q6으로 걸어 두었습니다.
- 공통 목록에 `SYS_EXTERNAL_VENDOR`(본인인증 업체 FK, 택배사)와 `SYS_STATUS_HIST`(상품 판매 등록 검수 상태, 선행 6)가 빠져 있었습니다. 창고 FK는 "WMS 설계 때"로 이미 적혀 있고, 2차 테이블을 가리키는 FK는 재고 정의서 차수 칸에 표시했습니다.
- 첫째 붙여넣기(진행 상황 요약)는 다른 대화의 오래된 요약이라 저장소와 다릅니다(재고 결정 65건·7개 테이블, 배송 "패키지", 이미 결정한 재고 추가 제안 7개를 미응답으로 적음 등). 쓰지 않습니다.

제 기록의 오류: 1차-1 결정 기록과 진행메모에 "`MBR_MEMBER.JOIN_AGE_GROUP_CD`가 NOT NULL"이라고 적었는데, 이 컬럼은 `MBR_JOIN_ATTRIBUTION`에 있습니다. 결론(가입 때 본인인증은 뺄 수 없음)은 그대로입니다.
#ex
**예시**
- 고객이 카드로 59,000원을 결제해 승인되면, 같은 UPDATE에서 정산 방식을 넣어야 CHECK를 통과합니다. 정산 방식은 카드사 가맹점 계약 테이블에서 옵니다.
- 상품 등록으로 니트 L 현재고 행을 만들 때는 안전 재고 이력 "신규 행 기본값" 1행도 함께 넣습니다.
#opt A
6개를 모두 1차에 더해 6개 도메인 49개로 하고(회원 10, 상품 11, 주문 4, 결제 8, 재고 6, 배송 10), 공통 목록에 두 테이블을 적습니다. 재고 정의서의 차수 칸(안전 재고 이력 "확인" → 1차, 월 마감 2차 → 1차)과 진행메모, CLAUDE.md, 1차-1 기록을 고칩니다
1차 흐름에서 CHECK나 FK 때문에 막히는 곳이 없습니다
1차 테이블이 6개 늘어납니다
#opt B
1차 흐름에서 쓰기를 막는 것만 더합니다: 가입 유입 경로, 카드사 가맹점 계약, 안전 재고 이력, 월 마감, 운임표(5개). PG 코드 대응은 1차에 코드 값을 애플리케이션 상수로 대신합니다
테이블이 하나 적습니다
결제 결정(2-4 A, PYC-2 B)과 다르게 구현하게 되어, 2차에 다시 고쳐야 합니다
#opt C

바꿀 것이 없습니다
카드 승인, 포장, 원장 기록, 가입이 1차에서 CHECK·FK에 막힙니다
#rec A
#reason
6개 모두 1차 흐름이 쓰는 행이 있고, 빼면 이미 정한 결정과 다르게 구현해야 합니다. 이 보충으로 1차 범위를 닫고, 수불 원장 컬럼 검토(IC-82)로 넘어가면 됩니다.
#choice A
#answer a
#apply
1차 테이블을 49개(회원 10, 상품 11, 주문 4, 결제 8, 재고 6, 배송 10)로 고치고, 공통 목록에 `SYS_EXTERNAL_VENDOR`, `SYS_STATUS_HIST`와 FK 적용 시점을 적었다(진행메모 "1차 범위", CLAUDE.md). 재고 정의서 차수 칸에서 안전 재고 이력과 월 마감을 1차로 바꾸고 1차 검토 순서에 월 마감을 넣었다. 1차-1 기록의 컬럼 위치 오류를 바로잡았다. 1차 범위는 이것으로 닫는다.
