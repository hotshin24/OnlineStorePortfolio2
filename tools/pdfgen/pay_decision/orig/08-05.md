## 8-5. 결제 요청 IP와 기기 정보

**무엇을 정하나요?**
결제를 시도할 때마다 요청 IP와 기기 정보를 결제 행에 남길지 정합니다. 남긴다면 얼마나 보관할지도 정합니다. 이 값은 부정 결제 분석(9-1)과 차지백 소명(9-3)에 쓰입니다.

**이미 정한 것**
- 주문 OC-92 C:
  - 주문 유입 정보(`ORD_ORDER_ATTRIBUTION`)에 판매 채널, OS, 주문 요청 IP가 있습니다.
  - IP는 평문 + TDE이고, 주문 일시부터 정책값 기간(3개월)이 지나면 배치가 NULL로 바꿉니다. 보관 기간과 처리방침 고지는 [확인 필요: 법무]입니다.
- 선행 5: IP는 암호화 대상이 아닙니다.
- 선행 10: 판매 채널은 `PC`, `MOBILE_WEB`, `APP` 3개이고, OS 컬럼을 따로 둡니다.
- 2-1 A: 결제 행은 시도마다 생깁니다. 추가 결제(5-10)는 주문 몇 주 뒤에도 생깁니다.

**예시로 보면**
1. **보통의 결제:** 주문을 만든 브라우저에서 바로 결제합니다. 결제 IP와 주문 IP가 같습니다.
2. **기기를 바꿔 다시 결제:** PC에서 주문하고 카드 한도로 실패했습니다. 휴대폰 앱에서 같은 주문을 다른 카드로 결제합니다. 두 시도의 IP와 채널이 다릅니다.
3. **추가 결제:** 3주 뒤 교환 배송비를 결제합니다. 주문 IP와 상관없는 새 요청입니다.
4. **도용 의심:** 짧은 시간에 해외 IP 하나에서 서로 다른 회원 계정으로 카드 결제가 30건 시도됩니다.
5. **차지백:** 4개월 뒤 카드사가 "본인이 결제하지 않았다"는 이의 제기를 보냅니다. 결제 당시 IP가 남아 있으면 소명 자료가 됩니다. 주문 IP는 3개월 뒤 이미 NULL입니다.

**선택지**

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | 결제 행에는 두지 않고, 주문 유입 정보의 IP·채널을 씁니다. | 컬럼이 늘지 않습니다. | 예시 2·3처럼 주문과 다른 요청의 정보가 남지 않습니다. 예시 4의 시도별 분석을 할 수 없습니다. |
| **B** | **결제 행마다 요청 IP, 판매 채널, OS를 남깁니다.**<br>• IP는 주문 OC-92 C와 같은 방식으로, 정책값 기간이 지나면 배치가 NULL로 바꿉니다.<br>• 보관 기간 정책값은 결제 도메인에 따로 둡니다. 차지백 이의 제기 기간을 고려해 9-3에서 기본값을 정합니다. | 예시 2·3·4가 시도 단위로 정확히 남습니다. 주문과 같은 방식이라 배치와 고지 문구를 함께 씁니다. 차지백 기간에 맞춰 보관 기간만 따로 조정할 수 있습니다. | 결제 행에 컬럼 3개가 늘어납니다. 보관 기간이 주문 IP와 다르면 처리방침에 두 기간을 적어야 합니다. |
| C | B와 같지만 IP를 결제 기록 보존 기간(5년) 동안 보관합니다. | 어떤 분쟁에도 IP가 남아 있습니다. | 목적(부정 결제 대응)에 비해 보관이 길어 최소 보관 원칙에 어긋날 수 있습니다 [확인 필요: 법무]. 주문 OC-92 C와 방향이 다릅니다. |

**추천: B.**
- 결제는 주문과 다른 시점, 다른 기기에서 일어날 수 있어 시도마다 남겨야 부정 결제를 분석할 수 있습니다.
- 보관 기간은 목적(차지백 소명)에 맞춰 정하되, 끝나면 지우는 방식은 주문과 같게 둡니다.

**B를 고르면 생기는 것 (이름은 후보)**
- 결제 행 컬럼:
  - `PAYMENT_REQUEST_IP`(`VARCHAR2(45)`)
  - `SALES_CHANNEL_CD`(CHECK `PC` / `MOBILE_WEB` / `APP`)
  - `OS_CD`
- 정책값(`CMM_CODE`): 결제 IP 보관 개월 수. 기본값은 9-3에서 정합니다.
- 기간이 지난 IP를 NULL로 바꾸는 배치는 결제 행 생성 일시를 기준으로 합니다. 주문 OC-92 C처럼 별도 일자 컬럼은 두지 않습니다.
- 기기 지문(FDS 업체가 주는 기기 식별 값)을 쓸지는 9-1에서 정합니다.
- [확인 필요: 법무] 처리방침에 결제 IP 수집 목적과 보관 기간을 고지하는 것
