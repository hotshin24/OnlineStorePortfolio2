## 3-4. 중복 요청 방지

**무엇을 정하나요?**
같은 요청이 두 번 들어와도 결제가 두 번 생기거나 승인이 두 번 나가지 않게 하는 장치를 정합니다. 결제에서 중복이 생기는 곳은 네 군데입니다.
1. 결제 시작(결제창 열기)
2. 승인 요청
3. 웹훅 수신 (3-5, 7-2에서 정함)
4. 취소 요청 (5-1에서 정함)

이 패턴은 1과 2를 정합니다.

**이미 정한 것**
- 선행 9: Redis 없이 중복 요청 키를 DB에 둡니다.
- 주문 3-3 A: 주문은 주문 행에 중복 방지 키 컬럼(`ORDER_REQUEST_KEY_VAL`, UK)을 둡니다.
  - 같은 키로 다시 오면 내용 해시를 비교합니다. 같으면 기존 주문을 돌려주고, 다르면 오류입니다(OC-66 B).
  - 공용 `SYS` 키 테이블은 고르지 않았습니다.
- 2-2 C: 주문 결제 중 승인된 행은 주문당 1건으로 DB가 막습니다(마지막 방어선).
- 3-1 B: 승인 상태는 7개이고, "승인 요청 중" 상태는 없습니다.

**예시로 보면**
1. **결제 버튼 더블클릭:**
   - [결제하기]가 0.2초 간격으로 두 번 눌려 결제 행 두 개(`-01`, `-02`)와 결제창 두 개가 열리려 합니다.
   - 두 결제창에서 모두 인증하면 승인 시도도 두 번 나갑니다. 2-2 C의 UK가 두 번째 승인 기록을 막지만, PG에서는 이미 돈이 빠져나간 뒤라 즉시 취소해야 합니다.
2. **인증 결과 중복 도착:** 고객이 인증을 마친 뒤 결과 화면에서 새로고침을 누릅니다. 같은 인증 결과가 우리 서버에 두 번 도착합니다.
3. **승인 요청이 겹침:** 첫 번째 승인 요청이 PG 응답을 기다리는 동안(3초), 두 번째 요청도 결제 행이 아직 `AUTHENTICATED`인 것을 보고 승인을 요청합니다.
4. **정상 재시도:** 한도 초과로 실패한 뒤 고객이 다른 카드로 다시 결제합니다. 이것은 중복이 아니라 새 시도이므로 새 결제 행이 생겨야 합니다.

**선택지**

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | **주문과 같은 방식**으로 막습니다.<br>• 결제 시작(예시 1): 결제 화면이 발급한 키를 결제 행의 중복 방지 키 컬럼(UK)에 넣습니다. 같은 키로 다시 오면 기존 결제 행을 돌려줍니다. 예시 4는 화면이 새 키를 발급합니다.<br>• 승인 요청(예시 2·3): 승인 요청 일시 컬럼을 조건부 UPDATE로 선점합니다. `WHERE 상태 = 'AUTHENTICATED' AND 승인 요청 일시 IS NULL`이고, 1행을 바꾼 요청만 PG를 부릅니다. 나머지 요청은 현재 상태를 돌려줍니다. | 주문 3-3 A와 규칙이 같습니다. 예시 1은 결제 행이 하나만 생겨 결제창도 하나만 열립니다. 예시 3은 DB 한 문장으로 한 요청만 PG를 부릅니다. 상태 값을 늘리지 않습니다(3-1 B 유지). | 컬럼 2개가 늘어납니다. 승인 요청 일시를 선점한 뒤 응답 없이 끝난 행은 3-7(결과 불명)에서 처리해야 합니다. |
| B | 결제·취소·클레임이 함께 쓰는 공용 중복 요청 키 테이블(`SYS`)을 둡니다. 승인 요청 선점은 A와 같습니다. | 도메인마다 같은 테이블 하나로 처리합니다. | 주문 3-3 A에서 고르지 않은 방식이라 도메인마다 방식이 갈립니다. 키 정리 배치와 테이블이 하나 늘어납니다. |
| C | 별도 키 없이 2-2 C의 UK와 PG의 중복 거부에 맡깁니다. | 컬럼이 늘지 않습니다. | 예시 1에서 결제창이 두 번 열리고, 승인이 두 번 나간 뒤에야 막힙니다. 이중 승인을 바로 취소하는 일이 잦아집니다. |

**추천: A.**
- 주문과 같은 규칙이라 개발과 운영 모두 하나만 이해하면 됩니다.
- "승인 요청 중" 상태를 새로 만들지 않고 일시 컬럼으로 선점하므로, 3-1 B의 상태 단순함을 유지합니다.

**A를 고르면 생기는 것 (이름은 후보)**
- `PAYMENT_REQUEST_KEY_VAL`(결제 요청 중복 방지 키, `VARCHAR2(64)`, UK). 같은 키에 다른 내용이 오면 오류로 처리합니다(주문 OC-66 B와 같음).
- `APPROVAL_REQUESTED_AT`(승인 요청 일시): 조건부 UPDATE로 선점합니다.
- CHECK: 상태가 `APPROVED`면 `APPROVAL_REQUESTED_AT`이 NOT NULL. 단, 자동 승인 수단(3-3 A)은 제외합니다.
- 넘기는 것:
  - 승인 요청을 선점한 뒤 응답이 없는 행 → 3-7
  - 웹훅 중복 → 3-5·7-2
  - 취소 중복 → 5-1
