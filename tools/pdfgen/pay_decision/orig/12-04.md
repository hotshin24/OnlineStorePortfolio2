## 12-4. 예치금 출금 요청과 원장 보관

앞에서 넘긴 두 가지를 함께 정합니다.
- 12-2에서 넘긴 출금 요청 테이블의 구조
- 12-1에서 넘긴 적립금·예치금 원장의 보관 방식

서로 다른 질문이라 선택지를 둘로 나눴습니다.

**이미 정한 것**
- 선행 15: 예치금 출금 요청 테이블을 둡니다. 환불 계좌는 회원 테이블에 있습니다.
- 회원 도메인:
  - 환불 계좌는 1원 인증을 받아야 합니다(43-2 C). 개명하면 재인증이 필요합니다(C-17).
  - 탈퇴 신청 때 자동 출금하고, 실패해도 7일 유예가 끝나면 탈퇴를 확정합니다(28-7, L2).
- 12-2 A: 출금은 현금성 입금 행에서만 차감합니다.
- 8-3 B·5-6 A: 환불 계좌는 행에 암호문으로 복사하고, 예금주를 확인합니다.
- 7-4 A: "출금 완료 ≠ 회사 계좌 출금 내역"을 대사합니다. 출금 내역은 정산 도메인에 있습니다.
- 선행 11: 행별 기한 테이블은 나눠서 DELETE합니다.

---

### 질문 1. 출금 요청 처리

**예시로 보면**
1. **요청:** 고객이 현금성 예치금 5만 원 출금을 요청합니다. 처리는 다음 영업일 오전 이체 배치가 합니다.
2. **요청 중 사용:** 이체 전에 고객이 같은 예치금 3만 원으로 주문합니다. 5만 원이 다 출금되면 3만 원이 이중으로 쓰입니다.
3. **이체 실패:** 계좌 해지로 이체가 실패합니다. 5만 원을 예치금으로 되돌려야 합니다.
4. **탈퇴 자동 출금:** 탈퇴 신청으로 자동 요청이 생깁니다. 7일 안에 실패가 계속되어도 탈퇴는 확정됩니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | **요청할 때 원장에서 바로 차감합니다.**<br>• 요청 행: 요청 유형(고객 / 탈퇴 자동), 금액, 계좌 복사(은행, 번호 암호문·마스킹, 예금주), 1원 인증 확인 일시, 상태(요청 / 이체 중 / 완료 / 실패 / 취소), 이체 결과, 실패 사유, 재시도 횟수<br>• 요청하는 순간 원장에 출금 행을 쓰고 현금성 입금 건에서 차감합니다(예시 2 방지).<br>• 실패하거나 취소하면 출금 취소 행으로 같은 입금 건에 되돌립니다(예시 3). | 잔액이 늘 실제 쓸 수 있는 금액이라 이중 사용이 없습니다. 12-1·12-3의 복원 방식(원래 건으로 되돌림)과 같습니다. 탈퇴 자동 출금도 같은 흐름입니다. | 실패한 요청마다 원장 행이 두 개(출금, 출금 취소)씩 생깁니다. |
| B | 이체가 완료될 때만 원장에서 차감합니다. 요청 중인 금액은 회원별 "출금 대기 금액"으로 따로 빼 둡니다. | 실패해도 원장 행이 생기지 않습니다. | 사용 가능 금액 = 잔액 − 출금 대기 금액이라 계산할 곳이 둘이 됩니다. 어느 입금 건에서 빠질지가 완료 때까지 정해지지 않습니다. |
| C | 요청 테이블 없이 원장 출금 행에 계좌와 상태를 함께 둡니다. | 테이블이 줄어듭니다. | 선행 15(출금 요청 테이블)와 다릅니다. 원장에 상태와 개인정보가 섞여, 계좌 파기(8-6) 때 원장 행을 고쳐야 합니다. |

**추천: A.** 출금은 요청 순간에 묶어 두어야 이중 사용을 막습니다. 실패 때 되돌리는 경로는 이미 적립금 복원에서 쓰는 방식입니다.

**A를 고르면 생기는 것 (이름은 후보)**
- `PAY_DEPOSIT_WITHDRAWAL_REQUEST`:
  - 계좌는 암호문 + 마스킹(8-3 B)입니다.
  - 개인정보 보유 공통 컬럼 4개(8-6 A)를 둡니다.
  - 상태 CHECK와 상태 전이 규칙을 둡니다.
- 이체 실행과 회사 계좌 내역은 정산 도메인으로 넘깁니다. 결제 도메인은 요청과 결과만 가집니다.
- 탈퇴 확정 뒤에도 출금되지 않은 예치금의 처리(보관, 재연락)는 회원 도메인을 다시 볼 때 확인할 사항으로 남깁니다.

### 질문 2. 적립금·예치금 원장의 보관과 삭제

**예시로 보면**
1. **오래된 예치금:** 2026년에 들어온 예치금 1만 원이 2033년에도 남아 있습니다. 예치금에는 유효기한이 없습니다.
2. **끝난 적립 건:** 2026년 적립금이 2027년에 다 쓰였거나 소멸했습니다.
3. **월 파티션이라면:** 2026년 1월 파티션을 지우면 그 달 입금 행을 가리키는 2033년 차감 기록이 깨집니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | **파티션 없이 둡니다.** 남은 금액이 0인 적립·입금 건은 그 건과 연결된 차감·사용 행의 마지막 변동일부터 5년(정책값)이 지나면 함께 나눠서 DELETE합니다. 남은 금액이 있는 건(예시 1)은 지우지 않습니다. | 예시 1·3의 문제가 없습니다. 5년은 거래 기록 보존(전자상거래법)과 같습니다. 원장에는 회원 ID 말고 개인정보가 없어 파기 컬럼이 필요 없습니다. | 삭제 배치가 건 단위로 연결 행을 찾아야 해 복잡합니다. |
| B | 생성 월 인터벌 파티션을 두고, 5년 뒤 파티션을 제거합니다. | 삭제가 빠릅니다. | 예시 1·3처럼 남은 건과 차감 기록이 깨집니다. 차감 기록 FK 때문에 제거 자체가 막힙니다(ORA-02266). |
| C | 지우지 않고 영구 보관합니다. | 가장 단순합니다. | 행이 계속 쌓입니다. 보존 의무를 넘는 보관입니다. |

**추천: A.** 적립 건은 기한과 남은 금액이 행마다 달라 시간순 파티션과 맞지 않습니다. 선행 11의 "행별 기한 테이블은 나눠서 DELETE"에 해당합니다.

**A를 고르면 생기는 것**
- 정책값: 원장 보관 연수(5)
- 삭제 배치(Oracle 스케줄러): 남은 금액 0 + 마지막 변동 5년 경과 건을 찾아 차감 기록 → 원장 행 순으로 나눠 지웁니다.
- 함수 기반 인덱스: 남은 금액이 0인 건만 마지막 변동일 키를 갖게 합니다(삭제 대상 찾기).
