## 11-3. 시퀀스 CACHE와 고빈도 테이블

**무엇을 정하나요?**
선행 1에서 "어느 테이블이 고빈도인지는 각 도메인에서 정한다"고 남긴 것을 결제 도메인 테이블에 대해 정합니다. 고빈도 테이블은 CACHE 100, 저빈도 테이블은 CACHE 20입니다.

**이미 정한 것**
- 선행 1:
  - 테이블별 SEQUENCE `SEQ_{테이블}`을 씁니다.
  - `INCREMENT BY 1`입니다.
  - CACHE는 고빈도 100, 저빈도 20입니다.
- 주문 도메인: 주문, 주문 상품, 할인 배분, 상태 이력은 100이고, 나머지는 20입니다.
- 2-8 B: 결제번호는 주문번호 + 3자리 순번입니다. 시퀀스에서 만들지 않으므로 시퀀스 번호가 비어도 업무 번호에는 영향이 없습니다.
- 7-6 B: PG 성능 집계는 복합 PK라 시퀀스가 없습니다.

**예시로 보면**
연매출 4,700억 원, 평균 객단가 약 9만 원이면 하루 주문은 약 1.4만 건입니다. 행사일에는 3~5배로 늡니다.
1. **결제 행:** 실패·재시도를 합쳐 주문의 약 1.3배이므로 하루 2만 건 안팎입니다.
2. **PG 호출 로그:** 결제마다 인증, 승인, 조회 호출이 쌓여 하루 6만~10만 행입니다.
3. **차지백:** 한 달에 몇 건입니다.
4. **DB 재시작:** CACHE 100이면 재시작할 때 최대 99개 번호가 비어 버립니다. 대리 PK라 문제는 없습니다.

**선택지**

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | **거래·로그 테이블은 100, 나머지는 20으로 둡니다.**<br>• 100: 결제, 취소, PG 호출 로그, 웹훅 수신함, 현금영수증 발급<br>• 20: 세금계산서, 차지백, 대사 실행·불일치, PG 장애 기록, 결제 수단 × PG 설정 | 행사일 동시 결제에서 시퀀스 경합을 줄입니다. 주문 도메인의 기준(거래 테이블 100)과 같습니다. | 고빈도 목록을 문서로 관리해야 합니다. |
| B | 모두 20으로 둡니다. | 규칙이 하나입니다. | PG 호출 로그처럼 하루 10만 행 테이블에서 시퀀스 딕셔너리 갱신이 잦아집니다. |
| C | 모두 100으로 둡니다. | 경합 걱정이 없습니다. | 행이 적은 테이블에서 비는 번호만 늘어납니다. 선행 1의 구분 취지와 맞지 않습니다. |

**추천: A.**
- 결제 테이블은 주문과 같은 속도로 늘고, 로그 테이블은 그보다 몇 배 빨리 늘어 100이 맞습니다.
- 현금영수증 발급은 현금성 결제마다 자동 발급(6-3 C)되고 취소·재발급(6-4 A)이 붙어 결제 행 수에 가깝습니다. 그래서 100에 넣었습니다.

**A를 고르면 생기는 것**
- `SEQ_PAY_PAYMENT`, `SEQ_PAY_PAYMENT_CANCEL`, `SEQ_PAY_PG_API_LOG`, `SEQ_PAY_PG_WEBHOOK_INBOX`, `SEQ_PAY_CASH_RECEIPT`: `CACHE 100`
- 나머지 결제 도메인 시퀀스: `CACHE 20`
- 테이블 정의서의 "PK" 칸에 시퀀스 이름과 CACHE 값을 적습니다(주문과 같은 형식).

<!--ANSWER-->
**사용자:** a

11-3은 A로 메모해 두었습니다. 결제, 취소, PG 호출 로그, 웹훅 수신함, 현금영수증 발급은 CACHE 100이고, 나머지는 CACHE 20입니다.
