## 7-1. PG 연동 로그

**먼저 알릴 해석 문제**
- 선행 6에는 "외부 연동 로그는 **도메인·업체별** 전용 테이블에 둔다(`SYS_INTERFACE_LOG`는 쓰지 않는다)"고 적혀 있습니다.
- 이 문장은 두 가지로 읽을 수 있습니다.
  - ① 도메인별 전용 테이블 하나에 업체 코드 컬럼을 둔다
  - ② PG 업체마다 테이블을 따로 만든다
- 아래 선택지 A는 ①, B는 ②의 해석입니다. 고르시는 안이 선행 6의 해석이 되므로 함께 확인해 주세요.

**무엇을 정하나요?**
우리가 PG API를 호출한 기록(승인, 취소, 조회, 빌링 결제, 가상계좌 발급, 현금영수증 발급 등)을 어떤 테이블에 어떤 내용으로 남길지 정합니다. 웹훅 수신 기록은 7-2에서 정합니다.

**이미 정한 것**
- 선행 4: 로그는 파티션 단위로 제거합니다.
- 선행 6: 범용 연동 로그 테이블은 쓰지 않습니다.
- 3-2 C: 결제 상태 이력 테이블을 두지 않으므로, 상세 흐름과 원문은 PG 로그가 맡습니다. PG 로그 보관 기간과 5년 보존 의무는 8-6·11-2에서 맞춥니다.
- 3-7 A, 5-9 A: 결과 불명과 취소 재시도에서 PG 조회를 반복합니다. 조회 호출도 로그에 남습니다.
- 주문 OC-67 A: 파티션을 제거하는 큰 테이블을 다른 테이블이 FK로 참조하면, 그 FK 때문에 파티션 제거가 막힙니다(ORA-02266).

**예시로 보면**
1. **승인 호출:** 10:00:41.120 요청 → 10:00:43.870 응답(2.75초), 결과 코드 `0000`
2. **시간 초과:** 10초 동안 응답이 없습니다. 응답 컬럼은 비어 있고, 결과는 "시간 초과"입니다.
3. **장애 분석:** 금요일 밤 PG-가의 평균 응답 시간이 0.8초에서 9초로 늘었습니다. 시간대별·PG별로 응답 시간과 실패율을 집계합니다(7-6).
4. **분쟁:** 고객이 "결제창에서 취소했는데 돈이 빠졌다"고 합니다. 그 결제의 PG 요청·응답 원문을 시간순으로 봅니다.
5. **규모:** 결제 하루 2만 건 × 호출 평균 3번(승인, 조회, 취소 등)이면 하루 6만 행입니다. 원문을 포함하면 행 하나가 수 KB입니다.

**선택지**

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | **결제 도메인 PG 호출 로그 테이블 하나**에 모든 PG의 호출을 담습니다(해석 ①).<br>• 컬럼: PG 업체 코드, API 종류, 결제 ID, 취소 ID, 결제번호·취소 요청번호, 요청·응답 일시, 소요 시간, HTTP 상태, PG 결과 코드·메시지, 성공 여부, 요청·응답 원문(민감값 가린 JSON)<br>• 월 단위 파티션이고, 보관 기간이 지나면 파티션을 제거합니다.<br>• 결제 ID에 FK를 걸지 않습니다(결제 파티션 제거를 막지 않게). | 예시 3의 PG별 비교를 한 테이블에서 합니다. PG가 늘어도 테이블은 그대로입니다. 범용 테이블이 아니라 결제 도메인 전용이라 선행 6의 취지(`SYS` 범용 금지)를 지킵니다. | PG마다 원문 형식이 달라 원문은 JSON 한 컬럼에 담아야 합니다. |
| B | PG 업체마다 로그 테이블을 따로 둡니다(해석 ②). | PG별 응답 필드를 컬럼으로 풀어 둘 수 있습니다. | PG가 늘 때마다 테이블이 늡니다. 예시 3의 비교에 UNION이 필요합니다. 테이블 최소화(규칙 5)와 맞지 않습니다. |
| C | 로그를 DB에 두지 않고, 애플리케이션 로그(파일·외부 로그 도구)에 둡니다. | DB 부담이 없습니다. | 예시 4의 분쟁 근거가 DB 밖에 있어 보존 의무와 접근 통제를 따로 관리해야 합니다. 결제 행과 조인해 분석할 수 없습니다. |

**추천: A.**
- 장애 비교와 분쟁 대응 모두 "여러 PG를 같은 기준으로 보는 것"이 핵심이라 테이블 하나가 맞습니다.
- 선행 6이 막으려던 것은 모든 도메인이 쓰는 범용 로그(`SYS_INTERFACE_LOG`)입니다. 결제 도메인 전용 테이블은 그 취지에 맞는다고 봅니다.

**A를 고르면 생기는 것 (이름은 후보)**
- `PAY_PG_API_LOG`:
  - 월 인터벌 파티션
  - 결제 ID·취소 ID는 FK 없이 인덱스만 둡니다(LOCAL)
  - 원문은 `JSON` 타입이고, 요청 원문과 응답 원문을 나눠 둡니다
- 원문에서 가릴 값(카드번호 전체, 빌링키, 계좌번호, 휴대폰 번호 등)과 가리는 방법은 8-4에서 정합니다.
- 보관 기간과 파티션 제거 주기는 11-2에서 정합니다. 5년 보존 대상 값은 결제 행에 이미 있도록 맞춥니다(8-6).
- 선행 6의 해석 기록: "외부 연동 로그는 도메인별 전용 테이블(업체 코드 컬럼)"로 CLAUDE.md에 적을지는 문서 작업 때 여쭙겠습니다.

**사용자:** c

7-1은 C로 확정하기 전에 확인할 것이 있습니다. C는 이미 정한 결정 하나와 충돌하고, 다른 두 결정이 기대던 전제를 바꿉니다.

**충돌하는 결정**

2. **3-2 C (전제 변경):** 상태 이력 테이블을 두지 않은 이유가 "상세 흐름과 원문은 PG 로그가 맡는다"였습니다. C를 고르시면 분쟁 때 근거(예시 4)를 DB 밖에서 찾아야 합니다.
3. **보존·접근 통제 (전제 변경):** PG 원문에는 마스킹된 카드번호, 휴대폰 번호 같은 개인정보가 들어 있습니다. DB 밖에 두면 개인정보 안전성 확보조치(접근 권한, 접속 기록, 보관 기간)를 외부 도구에서 따로 갖춰야 합니다.

웹훅 수신 기록(7-2)과 대사(7-3)는 C와 상관없이 정할 수 있습니다.
