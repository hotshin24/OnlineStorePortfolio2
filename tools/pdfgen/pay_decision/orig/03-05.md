## 3-5. 결과 수신 경로와 웹훅 순서 역전

**무엇을 정하나요?**
결제 결과는 네 경로로 들어옵니다. 경로마다 도착 순서가 보장되지 않습니다.
- **동기 응답:** 우리가 승인을 요청하고 받는 응답
- **브라우저 복귀:** 결제창이 인증 결과를 들고 돌아오는 것
- **웹훅:** PG가 우리 서버로 보내는 알림. 가상계좌 입금, PG 쪽 취소 등에 쓰입니다.
- **PG 조회:** 우리가 PG에 상태를 물어보는 것

이 패턴은 결과가 서로 다른 순서로 와도 결제 행이 틀린 상태가 되지 않게 하는 규칙입니다. 웹훅 저장 구조는 7-2에서 정합니다.

**이미 정한 것**
- 3-1 B: 승인 상태는 7개이고, 한 방향으로 흐릅니다.
- 3-2 C: 결과 확정 경로 코드(`SYNC_RESPONSE`, `WEBHOOK`, `PG_INQUIRY`, `MANUAL`)를 남깁니다.
- 3-3 A: 승인 전에 금액을 검증합니다.
- 3-4 A: 승인 요청은 조건부 UPDATE로 한 요청만 선점합니다.
- 선행 6: PG 연동 로그는 결제 도메인 전용 테이블에 둡니다(7-1).

**예시로 보면**
1. **웹훅이 먼저 도착:** 승인 동기 응답이 네트워크 지연으로 늦는 사이, "승인 완료" 웹훅이 먼저 옵니다. 결제 행은 아직 `AUTHENTICATED`입니다.
2. **옛 웹훅이 늦게 도착:** 가상계좌에 입금된 뒤 고객이 환불받았습니다. "입금 완료" 웹훅이 재전송으로 "환불" 처리 뒤에 다시 옵니다. 그대로 적용하면 상태가 거꾸로 돌아갑니다.
3. **같은 웹훅 3번:** PG가 우리 응답을 못 받았다고 판단해 같은 웹훅을 1분 간격으로 3번 보냅니다.
4. **가짜 웹훅:** 누군가 웹훅 주소를 알아내 "입금 완료"를 보냅니다. 그대로 믿으면 입금 없이 주문이 결제 완료가 됩니다.
5. **동기 응답과 조회가 겹침:** 결과 불명 행을 조회 배치가 "승인"으로 바꾸는 순간, 늦게 온 동기 응답도 "승인"을 쓰려 합니다.

**선택지**

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | **웹훅 내용을 바로 적용**하되, 앞으로만 가는 조건부 UPDATE로 막습니다(`WHERE 상태 IN (허용된 이전 상태)`). 이미 지나간 상태로 되돌리는 웹훅은 무시하고 로그에 "무시"로 남깁니다. | 반영이 가장 빠릅니다. 예시 1·2·3·5를 조건부 UPDATE로 막습니다. | 예시 4는 서명 검증에만 기댑니다. 웹훅 내용이 PG마다 달라 해석 코드가 PG 수만큼 늘어납니다. |
| B | PG가 준 이벤트 시각을 저장하고, **더 늦은 시각의 이벤트만** 적용합니다. | 순서 역전을 시각으로 판단합니다. | PG 이벤트 시각의 정밀도와 신뢰성이 PG마다 다릅니다. 예시 4를 막지 못합니다. 결제 행에 이벤트 시각 컬럼이 늘어납니다. |
| **C** | **웹훅은 "조회하라"는 신호로만 씁니다.** 웹훅을 받으면 로그에 남기고, 그 결제를 PG에 조회해 조회 결과를 A의 조건부 UPDATE로 적용합니다. 동기 응답과 조회 배치도 같은 적용 함수 하나를 거칩니다. | 예시 4의 가짜 웹훅은 PG 조회에서 걸러지므로 아무 효과가 없습니다. 예시 2는 조회가 "현재 상태"를 돌려주므로 순서 문제가 사라집니다. 해석 코드가 PG별 "조회 응답" 하나로 줄어듭니다. | 웹훅마다 PG 조회 1번이 더 듭니다(가상계좌 입금 등 하루 수천 건 수준). PG 조회 API가 장애면 반영이 늦어집니다(7-5). |

**추천: C.**
- 결제에서 가장 위험한 것은 "돈이 안 들어왔는데 들어왔다고 믿는 것"입니다. 웹훅 내용을 믿지 않고 PG의 현재 상태로 확인하면 가짜 웹훅과 순서 역전을 한 번에 막습니다.
- 추가 조회 비용은 웹훅이 오는 건수(가상계좌 입금, PG 쪽 이벤트)에만 생겨 작습니다.

**C를 고르면 생기는 것**
- 허용 전이표(설명에 적고, 애플리케이션 적용 함수가 지킴):
  - `READY` → `AUTHENTICATED`, `WAITING_DEPOSIT`, `APPROVED`, `FAILED`, `UNKNOWN`, `EXPIRED`
  - `AUTHENTICATED` → `APPROVED`, `FAILED`, `UNKNOWN`, `EXPIRED`
  - `UNKNOWN` → `APPROVED`, `FAILED`
  - `WAITING_DEPOSIT` → `APPROVED`, `EXPIRED`
  - `EXPIRED`·`FAILED` → `APPROVED`: PG 조회로 승인이 확인될 때만 허용합니다. 바로 자동 취소합니다(3-8).
- 결과 확정 경로 코드의 `WEBHOOK`은 "웹훅을 계기로 한 조회로 확정"을 뜻합니다. 코드 설명에 적습니다.
- 웹훅 로그에 적용 결과(적용 / 무시 / 조회 실패)를 남깁니다. 구조는 7-2에서 정합니다.

**사용자:** c

3-5는 C로 메모해 두었습니다. 웹훅은 PG에 조회하라는 신호로만 쓰고, 상태는 PG 조회 결과를 앞으로만 가는 조건부 UPDATE로 반영합니다.
