## 7-6. 결제 감시 지표

**무엇을 정하나요?**
결제 도메인에서 무엇을 계속 지켜보고, 그 값을 어디서 계산하고 어디에 남길지 정합니다. 앞 패턴에서 "감시 배치·알림"으로 넘긴 것들을 한곳에 모읍니다.

**지금까지 감시 대상으로 넘긴 것**

|---|---|---|
| PG 상태 | 수단별·PG별 승인 성공률, 응답 시간 | 7-1 C 호출 요약 로그 |
| 밀린 일 | 결과 불명 건수와 가장 오래된 것의 경과 시간 | 3-7 A |

**예시로 보면**
1. **실시간:** 지금 결과 불명 결제가 37건이고, 가장 오래된 것이 18분째입니다. 기준(10건 또는 15분)을 넘었으므로 알림이 갑니다.
2. **추세:** 지난 6개월 동안 PG-가와 PG-나의 카드 승인 성공률과 응답 시간을 비교해 수수료 재협상 자료로 씁니다. 그런데 호출 로그는 보관 기간이 지나 이미 지워졌습니다(11-2).
3. **법정 기한:** 내일이 기한인 환불 미이행 건이 4건입니다.

**선택지**

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | 지표 테이블 없이, 모든 지표를 기존 테이블에서 바로 계산합니다(뷰·쿼리). 기준값은 `CMM_CODE` 정책값에 둡니다. | 테이블이 늘지 않습니다. 밀린 일은 이미 만든 함수 기반 인덱스로 빠르게 셉니다. | 예시 2의 장기 추세는 로그가 지워지면 계산할 수 없습니다. 성공률·응답 시간 집계를 큰 로그 테이블에서 자주 돌려야 합니다. |
| **B** | **A + PG 성능 집계 테이블**을 둡니다.<br>• 밀린 일과 법정 기한은 A처럼 기존 테이블에서 바로 셉니다.<br>• PG별·수단별·5분 단위로 호출 수, 성공 수, 실패 코드별 수, 응답 시간(평균·p95)을 Oracle 스케줄러가 집계해 저장합니다(선행 11: 집계는 스케줄러).<br>• 집계 테이블은 로그보다 오래 보관합니다(예: 3년). | 예시 2의 장기 비교가 로그 삭제와 상관없이 됩니다. 대시보드가 작은 집계 테이블만 읽어 빠릅니다. 장애 감지(7-5)도 이 집계를 봅니다. | 집계 테이블 1개와 스케줄러 작업이 늘어납니다. 5분 지연이 있어, 실시간 장애 감지에는 최근 5분 로그를 직접 함께 봐야 합니다. |
| C | DB에는 아무것도 두지 않고 외부 모니터링 도구(APM)에서 지표를 만듭니다. | DB 부담이 없습니다. | 법정 기한과 밀린 일은 DB를 봐야만 알 수 있어, 결국 DB 쿼리가 필요합니다. |

**추천: B.**
- 밀린 일과 기한은 "지금 DB에 있는 행"이 정답이라 바로 세는 것이 맞습니다. 이미 함수 기반 인덱스를 두었습니다.
- PG 성능은 계약과 라우팅 결정(1-5)에 쓰는 장기 자료라, 로그가 사라지기 전에 작게 요약해 두어야 합니다.

**B를 고르면 생기는 것 (이름은 후보)**
- `PAY_PG_METRIC_5MIN`:
  - PK: (PG 업체 코드, 결제 수단 코드, API 종류, 집계 시작 시각)
  - 컬럼: 호출 수, 성공 수, 시간 초과 수, 평균·p95 응답 시간(ms)
  - 월 파티션, 3년 보관(정책값)
- 실패 코드별 건수는 JSON 한 컬럼에 담습니다(코드가 PG마다 달라서).
- 감시 기준값(`CMM_CODE` 정책값): 결과 불명 건수·경과 시간, 웹훅 미처리, 성공률 하한, p95 상한, 기한 임박 일수
- 알림 발송은 알림 도메인(`NTF`)으로 넘깁니다. 관리자 대상 알림입니다.
