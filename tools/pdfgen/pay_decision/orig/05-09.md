## 5-9. 취소 실패와 재시도

**무엇을 정하나요?**
PG 취소 요청이 실패하거나 응답이 없을 때 어떻게 다시 시도할지 정합니다. 그러면서 같은 취소가 두 번 처리되는 사고(이중 취소)를 어떻게 막을지도 정합니다.

**이미 정한 것**
- 5-1 B:
  - 취소 행의 상태는 `REQUESTED` / `COMPLETED` / `FAILED`입니다.
  - 요청할 때 결제 행의 처리 중 금액에 더해 금액을 잡아 둡니다.
  - 실패하면 처리 중 금액에서 뺍니다.
- 3-6 A: PG 호출은 트랜잭션 밖에서 합니다. 잠금 순서는 주문 → 결제입니다.
- 3-7 A: 승인 결과 불명은 PG 조회로 확정합니다. 조회 일정 컬럼(`INQUIRY_CNT`, `NEXT_INQUIRY_AT`, `LAST_INQUIRY_AT`)이 있습니다.
- 5-6 A: 계좌 송금이 실패하면 그 행은 실패로 두고, 새 계좌로 새 취소 행을 만듭니다.
- 5-8 A: 취소 행에 법정 기한일이 있습니다.

**예시로 보면**
1. **명확한 실패:** PG가 "일시 오류, 잠시 후 다시 시도"를 돌려줍니다. 돈은 나가지 않았습니다.
2. **응답 없음:** 30,000원 부분 취소를 요청했는데 시간 초과가 납니다. PG에서는 실제로 취소가 됐을 수도 있습니다.
3. **이중 취소:**
   - 예시 2에서 "실패"로 보고 새 취소 행으로 30,000원을 다시 요청합니다.
   - 첫 요청도 실제로 처리됐다면 PG에서 60,000원이 취소됩니다.
   - 부분 취소는 금액만 같으면 PG가 같은 요청인지 모를 수 있습니다.
4. **PG 잔액 부족:** 계좌이체 결제 취소는 PG가 몰에 줄 정산 예정액에서 돌려주는데, 그 잔액이 부족해 취소가 거절됩니다 [확인 필요: 계약 PG 정책].
5. **기한 임박:** 법정 기한일이 내일인데 세 번째 재시도도 실패했습니다.

**선택지**

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | **응답이 없으면 같은 취소 행을 유지하고, 조회한 뒤 재시도합니다.**<br>• 취소 행마다 고유한 취소 요청번호를 두고, PG에 중복 방지 키로 보냅니다. 같은 취소 행의 재시도는 항상 같은 번호를 씁니다.<br>• 응답이 없으면(예시 2) `REQUESTED`로 두고 3-7과 같은 조회 일정 컬럼으로 PG 취소 내역을 조회합니다. 처리됐으면 `COMPLETED`로 바꾸고, 없으면 같은 번호로 다시 요청합니다.<br>• 명확한 실패(예시 1·4)는 정책에 따라 자동 재시도하고, 최대 횟수를 넘으면 `FAILED`로 둔 뒤 운영자 확인 대상으로 올립니다.<br>• 기한이 가까운 행(예시 5)은 운영자 알림 우선순위를 높입니다. | 예시 3의 이중 취소를 두 겹으로 막습니다. 같은 행, 같은 번호이기 때문입니다. 승인 쪽(3-7)과 같은 규칙이라 배치를 공유합니다. | 취소 행에 컬럼이 몇 개 늘어납니다. PG가 중복 방지 키를 지원하는지 확인해야 합니다 [확인 필요: 계약 PG]. |
| B | 응답이 없으면 `FAILED`로 두고 새 취소 행으로 즉시 재시도합니다. | 단순하고 빠릅니다. | 예시 3의 이중 취소가 생깁니다. 5-7(과다 환불)의 원인을 스스로 만듭니다. |
| C | 실패하면 모두 운영자가 수동으로 처리합니다. | 자동 재시도 로직이 없습니다. | 하루 수백 건이면 사람이 감당하기 어렵고, 3영업일 기한을 놓치기 쉽습니다. |

**추천: A.**
- 취소의 결과 불명은 승인의 결과 불명과 같은 문제라, 같은 해법(조회 뒤 재시도)과 같은 배치를 씁니다.
- 고유 요청번호는 PG가 중복 방지 키를 지원하지 않아도 PG 취소 내역 조회에서 이 취소를 찾는 열쇠가 됩니다.

**A를 고르면 생기는 것 (이름은 후보)**
- 취소 행 컬럼:
  - `CANCEL_NO`(취소 요청번호, UK). 형식은 결제번호 + `-C` + 순번 2자리이고, 2-8 B와 같은 방식입니다.
  - 조회 일정 컬럼: `INQUIRY_CNT`, `NEXT_INQUIRY_AT`, `LAST_INQUIRY_AT`
  - 재시도 컬럼: `RETRY_CNT`, `NEXT_RETRY_AT`
  - `MANUAL_CHECK_REQUIRED_YN`(운영자 확인 필요)
  - 마지막 실패 사유: PG 오류 코드와 메시지
- 정책값(`CMM_CODE`): 자동 재시도 간격과 최대 횟수
- 5-1 B의 중복 방지 키(화면 요청 중복)와 `CANCEL_NO`(PG 요청 중복)는 막는 대상이 달라 둘 다 둡니다.
- `NEXT_INQUIRY_AT`, `NEXT_RETRY_AT`가 있는 행만 키를 갖는 함수 기반 인덱스를 둡니다(3-7과 같은 방식).

**사용자:** a

5-9는 A로 메모해 두었습니다. 응답이 없으면 같은 취소 행과 같은 취소 요청번호로 PG에 조회한 뒤 다시 시도합니다. 정해 둔 횟수를 넘기면 운영자 확인 대상으로 넘깁니다.
