## 2-8. 결제번호와 PG 거래번호

**무엇을 정하나요?**
결제 행에는 번호가 두 개 있습니다.
- **결제번호:** 우리가 만들어 PG에 "가맹점 주문번호"로 보내는 번호입니다(PG마다 `orderId`, `merchant_uid` 등으로 부름).
- **PG 거래번호:** PG가 승인 뒤 돌려주는 번호입니다(`tid`, `paymentKey` 등).

이 패턴에서는 결제번호의 형식과, 두 번호의 UNIQUE 처리를 정합니다.

**이미 정한 것**
- 선행 1·3: 업무 키는 `_NO`이고, 업무상 식별 가치가 있으면 UNIQUE를 겁니다.
- 선행 4: 재사용 금지 값은 일반 UK를 걸고, 물리 삭제 전에 `SYS_RESERVED_KEY`로 옮깁니다.
- 선행 13: (PG 업체 코드 + PG 거래번호)에 UK를 겁니다.
- 2-1 A: 결제 행은 PG를 부르기 전에 만들고, 결제번호도 이때 채웁니다. 재시도할 때마다 행이 하나씩 생깁니다.
- 2-2 C: 주문 결제 말고도 클레임 추가 결제(용도 `ADDITIONAL`)가 같은 주문 아래 생깁니다.
- 주문 3-5 A: 결제가 만료된 주문은 N일 뒤 물리 삭제합니다.

**예시로 보면**
주문번호가 `20261125-0001234`인 주문입니다.
1. **재시도:** 한도 초과로 첫 시도가 실패하고 두 번째에 승인됩니다. PG는 같은 결제번호의 재사용을 거부하므로 시도마다 새 번호가 필요합니다.
   - B 방식의 번호: `20261125-0001234-01`(실패), `20261125-0001234-02`(승인)
2. **추가 결제:** 2주 뒤 교환 배송비 6천 원을 결제합니다. 번호는 `20261125-0001234-03`입니다.
3. **PG 관리자 화면 조회:** 상담원이 고객이 알려 준 주문번호로 PG 관리자 화면에서 거래를 찾습니다. 결제번호가 주문번호로 시작하면 앞부분 검색으로 바로 찾을 수 있습니다.
4. **승인 전 행들:** "준비" 상태 행 수천 개는 아직 PG 거래번호가 NULL입니다. 모두 PG 업체 코드는 같습니다.
5. **만료 주문 삭제:** 결제 만료 주문을 지울 때 결제번호 `…-01`도 함께 지워집니다. 같은 번호가 다시 나오면 PG가 거부하거나, 대사(7-3)에서 다른 거래로 섞입니다.

**선택지 (결제번호 형식)**

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | 주문과 무관한 결제 전용 번호를 씁니다(예: `P` + 날짜 + 시퀀스 10자리). | 주문번호 형식과 묶이지 않습니다. | 예시 3에서 PG 화면의 번호만 보고는 어느 주문인지 모르므로 우리 시스템에서 다시 찾아야 합니다. |
| **B** | **주문번호 + 순번 3자리**입니다(예시 1·2). 순번은 주문 아래 결제 행 전체(재시도, 추가 결제)에 이어서 매깁니다. UK: (주문 ID, 순번) | 번호만 봐도 주문과 몇 번째 시도인지 압니다. PG 화면, 정산 파일, CS 어디서나 주문으로 바로 이어집니다. | 순번을 매길 때 주문 행을 잠가야 합니다(같은 주문에 두 시도가 동시에 생길 때). PG의 길이·문자 제한에 맞는지 확인해야 합니다 [확인 필요: PG 연동 문서]. |
| C | 결제 PK(`PAYMENT_ID`)를 그대로 보냅니다. | 번호를 따로 만들지 않습니다. | 내부 시퀀스가 밖으로 드러납니다. 개발·운영 DB가 같은 PG 테스트 MID를 쓰면 번호가 겹칩니다. A의 단점도 그대로 있습니다. |

**추천: B.**
- 결제 사고 대응은 대부분 "PG 화면 ↔ 우리 주문"을 오가는 일이라, 번호에서 주문이 보이는 것이 가장 큰 도움이 됩니다.
- 순번을 매길 때의 잠금은 2-1에서 결제 행을 만들 때 이미 주문 행을 다루는 시점이라 추가 부담이 작습니다.

**어느 안을 고르든 생기는 것: PG 거래번호의 UNIQUE**
- 선행 13의 UK(PG 업체 코드 + PG 거래번호)를 일반 복합 UK로 걸면 예시 4에서 문제가 생깁니다.
  - Oracle의 복합 UNIQUE는 한 컬럼이라도 값이 있으면 비교합니다. 그래서 ('PG-가', NULL) 행이 두 개 생기는 순간 중복 오류가 납니다.
- 함수 기반 UK로 겁니다: `(CASE WHEN PG 거래번호 IS NOT NULL THEN PG 업체 코드 END, PG 거래번호)`. 두 값이 모두 NULL인 행은 인덱스에 들어가지 않습니다.
- 결제번호는 재사용 금지 값이라 일반 UK를 걸고, 주문을 물리 삭제할 때 `SYS_RESERVED_KEY`로 옮깁니다(예시 5).

**B를 고르면 생기는 것 (이름은 후보)**
- `PAYMENT_NO`(결제번호, UK)
- `PAYMENT_SN`(주문 안 결제 순번). UK: (`ORDER_ID`, `PAYMENT_SN`)
- `PG_TRANSACTION_NO`(PG 거래번호) + 위 함수 기반 UK
- 카드 승인번호(2-4)는 카드사가 매기는 번호라 겹칠 수 있어 UNIQUE를 걸지 않습니다.
