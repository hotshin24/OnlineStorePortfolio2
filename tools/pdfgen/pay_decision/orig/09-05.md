## 9-5. 카드 본인 확인 방식 기록

**무엇을 정하나요?**
카드 결제 때 결제자가 카드 주인인지 어떤 방식으로 확인했는지를 어디에 어떻게 남길지 정합니다. 확인 방식은 앱카드, ISP, 안심클릭, 간편결제 인증, 원클릭 결제 비밀번호 등입니다. 이 기록은 차지백 소명(9-3)의 핵심 근거입니다.

**법에서 오는 조건**
- 여신전문금융업법 19조 2항: 가맹점은 신용카드로 거래할 때마다 카드를 본인이 정당하게 사용하는지 확인해야 합니다.
- 같은 법 16조: 부정 사용의 책임은 원칙적으로 카드사가 집니다. 다만 가맹점이 본인 확인을 소홀히 했으면 카드사가 가맹점에 손실을 넘길 수 있습니다. 그래서 "확인했다"는 기록이 가맹점을 지킵니다.

**이미 정한 것**
- 8-2 B: 원클릭 결제의 결제 비밀번호 확인 결과는 9-5에 남깁니다. 비밀번호 실패 횟수 관리는 회원 도메인(41-x)이 합니다.
- 3-1 B·3-2 C: 결제 행에 인증 완료 일시(`AUTHENTICATED_AT`)가 있습니다. 이력 테이블은 두지 않습니다.
- 3-3 A: 승인 전에 인증 금액(`AUTHENTICATED_AMT`)을 검증합니다.
- 9-1 A, 8-5 B: FDS 판정과 요청 IP·채널이 결제 행에 있습니다.
- 9-3 A: 차지백 사건 테이블이 있고, 결제 행의 값을 소명 자료로 씁니다.

**예시로 보면**
1. **앱카드 결제:** 고객이 카드사 앱에서 지문으로 인증합니다. PG가 "인증 방식 = 앱카드, 인증 결과 = 성공"을 돌려줍니다.
2. **원클릭 결제:** 우리 화면에서 6자리 결제 비밀번호를 확인한 뒤 빌링키로 결제합니다. 카드사 쪽 인증은 없습니다. 본인 확인은 우리가 했습니다.
3. **간편결제(네이버페이 카드):** 간편결제사가 자체 비밀번호로 확인합니다. 우리는 "간편결제사 인증"이라는 사실만 압니다.
4. **차지백:** 카드사가 "본인 확인을 어떻게 했나"를 묻습니다. 예시 1은 카드사 인증이라 카드사 책임입니다. 예시 2는 우리 비밀번호 확인 기록, IP, 기기를 내야 합니다.
5. **재시도:** 결제 비밀번호를 2번 틀리고 3번째에 맞췄습니다. 실패 2번은 회원 도메인 카운터에 있고, 결제 행에는 성공한 확인만 있으면 됩니다.

**선택지**

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | **결제 행에 본인 확인 컬럼 그룹을 둡니다.**<br>• 확인 주체 코드: 카드사·PG(`ISSUER`) / 간편결제사(`EASY_PAY_PROVIDER`) / 우리 몰(`MERCHANT`)<br>• 확인 방식 코드: `APP_CARD`, `ISP`, `SAFE_CLICK`, `EASY_PAY_AUTH`, `PAYMENT_PIN`, `NONE`<br>• 확인 일시는 기존 `AUTHENTICATED_AT`을 함께 씁니다.<br>• PG가 준 인증 결과 원본 코드(`PG_AUTH_RESULT_VAL`)<br>• CHECK: 상태가 `APPROVED`인 카드·원클릭 결제는 확인 방식이 NOT NULL이고 `NONE`이 아니어야 합니다. 예외는 정책으로 허용한 경우뿐입니다. | 예시 4의 질문에 결제 행 하나로 답합니다. 19조 2항의 "거래할 때마다 확인"을 DB가 강제합니다. 결제당 성공한 확인은 1번이라 1:1로 충분합니다. | 결제 행 컬럼이 3~4개 늘어납니다. 카드가 아닌 수단에서는 비어 있습니다. |
| B | 본인 확인 시도 테이블(결제 1 : 시도 N)을 따로 두고 실패한 확인까지 모두 남깁니다. | 예시 5의 실패까지 결제 단위로 남습니다. | 비밀번호 실패는 이미 회원 도메인이 셉니다(중복). 3-2 C(이력 테이블 없이 일시 컬럼)와 방향이 다릅니다. |
| C | 기록하지 않고 PG 거래 내역에 맡깁니다. | 만들 것이 없습니다. | 예시 2처럼 우리가 확인한 경우는 PG에 남지 않습니다. 차지백 소명을 할 수 없습니다. |

**추천: A.**
- 법이 요구하는 것은 "거래마다 확인했다"는 사실이고, 결제 1건에 성공한 확인은 1번이라 결제 행에 두는 것이 정확합니다.
- 확인 주체를 따로 두면 차지백 때 책임이 카드사 쪽인지 우리 쪽인지가 바로 갈립니다.

**A를 고르면 생기는 것 (이름은 후보)**
- 결제 행 컬럼:
  - `IDENTITY_VERIFIER_CD`(`ISSUER`, `EASY_PAY_PROVIDER`, `MERCHANT`)
  - `IDENTITY_VERIFICATION_METHOD_CD`(위 6개 값)
  - `PG_AUTH_RESULT_VAL`
- CHECK:
  - 원클릭이면 확인 주체는 `MERCHANT`이고 방식은 `PAYMENT_PIN`입니다.
  - 간편결제면 확인 주체는 `EASY_PAY_PROVIDER`입니다.
  - 카드·원클릭이 `APPROVED`이면 방식이 NOT NULL이고 `NONE`이 아닙니다.
- `NONE`(비인증 결제)을 허용할 경우가 있는지(예: PG 키인 결제 계약)는 [확인 필요: 계약 PG]입니다. 없으면 값 목록에서 뺍니다.
- 결제 비밀번호 실패 횟수와 잠금은 회원 도메인 그대로 둡니다.

<!--ANSWER-->
**사용자:** a

9-5는 A로 메모해 두었습니다. 결제 행에 본인 확인 주체, 확인 방식, PG 인증 결과를 둡니다. 승인된 카드·원클릭 결제는 확인 방식이 반드시 있어야 하도록 CHECK를 겁니다.
