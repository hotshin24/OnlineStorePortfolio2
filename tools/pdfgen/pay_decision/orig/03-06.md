## 3-6. 트랜잭션 경계와 잠금 순서

**무엇을 정하나요?**
승인이 확정되면 여러 테이블이 함께 바뀝니다. 결제 행, 주문 상태, 재고·쿠폰 예약 확정, 적립금·예치금 원장이 그 대상입니다. 이 패턴은 세 가지를 정합니다.
- 이 변경들을 어떤 트랜잭션으로 묶을지
- PG 호출(수 초~수십 초)을 트랜잭션 안에 둘지
- 여러 행을 잠글 때의 순서(교착 방지)

**이미 정한 것**
- 주문 OC-71 A, 10-7 A: 주문 상품 상태를 바꾸는 트랜잭션은 먼저 주문 행을 `SELECT … FOR UPDATE`로 잠급니다.
- 주문 6-9 A, 8-1 A, OC-122: 한도 검사는 회원 행(또는 한도 행)을 잠근 뒤 합산합니다.
- 2-7 A: 취소할 때는 결제 행을 잠그고 취소 누계를 더합니다.
- 3-4 A: 승인 요청 일시를 조건부 UPDATE로 선점합니다.
- 3-5 C: 동기 응답, 웹훅, 조회 결과는 모두 같은 적용 함수 하나로 반영합니다.

**예시로 보면**
1. **승인 흐름:** 고객 인증 → 우리 서버가 PG 승인 요청 → PG 응답(평소 1~3초, 혼잡하면 30초) → 결제 승인, 주문 결제 완료, 재고·쿠폰 예약 확정, 적립금 사용 확정
2. **PG가 느릴 때:** 승인 요청 동안 주문 행을 잠가 두면, 그 30초 동안 같은 주문의 다른 작업(주문 만료 배치, 상담원 메모)이 줄지어 기다립니다. 블랙프라이데이에는 DB 연결이 모자라 사이트 전체가 느려집니다.
3. **PG는 승인했는데 우리 DB 반영이 실패:** PG 승인 응답을 받은 직후 DB 저장이 실패합니다(배포 재시작 등). 돈은 빠져나갔는데 결제 행은 `AUTHENTICATED`에 머뭅니다. DB 롤백으로는 PG 승인을 되돌릴 수 없습니다.
4. **교착:**
   - 승인 처리는 주문 행 → 결제 행 순서로 잠급니다.
   - 같은 순간 결제 취소 처리가 결제 행 → 주문 행 순서로 잠급니다.
   - 서로 상대를 기다리다 Oracle이 한쪽을 ORA-00060으로 끊습니다.

**선택지**

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | **짧은 트랜잭션으로 나누고, PG 호출은 트랜잭션 밖에서 합니다.**<br>• T1: 승인 요청 일시를 선점하고 커밋합니다(3-4 A).<br>• PG를 호출합니다. 이때 잡고 있는 잠금은 없습니다.<br>• T2: 고정된 잠금 순서로 결과를 반영합니다. 결제 행, 주문 상태, 예약 확정, 원장을 한 트랜잭션으로 묶어 커밋합니다.<br>• 예시 3은 "승인 요청 일시가 있는데 N분째 `AUTHENTICATED`"인 행을 조회 배치가 찾아 PG 조회로 마저 반영합니다(3-7). | 예시 2에서 PG가 느려도 DB 잠금은 수 밀리초입니다. 예시 3은 구조적으로 복구됩니다. 우리 DB 안의 변경(결제, 주문, 예약, 원장)은 T2 하나로 원자적입니다. 잠금 순서가 정해져 있어 예시 4가 생기지 않습니다. | T1과 T2 사이 상태를 조회 배치가 메꿔야 합니다. 잠금 순서를 모든 개발자가 지켜야 합니다. |
| B | PG 호출을 포함해 트랜잭션 하나로 처리합니다. | 코드가 가장 단순합니다. | 예시 2를 그대로 겪습니다. 예시 3에서는 DB가 롤백되지만 PG 승인은 남아, 어차피 조회 복구가 필요합니다. |
| C | 결제 행만 승인으로 커밋하고, 주문 상태·예약 확정·원장은 아웃박스 이벤트로 비동기 처리합니다. | 결제 처리가 다른 도메인 장애에 덜 묶입니다. | 아웃박스 테이블과 이벤트 처리기가 늘어납니다. "결제는 승인인데 주문은 결제 대기"인 시간이 생겨 화면·CS가 헷갈립니다. 재고 예약 확정이 늦어집니다. |

**추천: A.**
- 외부 호출을 DB 트랜잭션 밖으로 빼는 것이 결제 시스템의 기본 원칙입니다. DB 롤백으로 외부 승인을 되돌릴 수 없으므로, 트랜잭션에 넣어도 얻는 것이 없습니다.
- 우리 DB 안의 변경은 T2 하나로 묶어 "결제는 승인인데 주문은 대기" 같은 중간 상태를 남기지 않습니다.

**A를 고르면 생기는 것: 잠금 순서 (정책명세 조문 후보)**
1. 주문 행 (주문 OC-71 A와 같음)
2. 결제 행 (주문 결제와 추가 결제가 함께 바뀌면 결제 ID 오름차순)
3. 회원 행 / 한도 행 (주문 6-9 A, 8-1 A)
4. 적립금·예치금 원장과 잔액 (12-5에서 정함)
5. 재고·쿠폰 예약 (각 도메인)

이어서 정할 것:
- 취소도 같은 순서를 따릅니다. 취소는 PG 호출 전에 DB에서 금액을 먼저 선점하는 방식으로 하고, 자세한 방식은 5-1과 5-9에서 정합니다.
- 조회 배치가 찾아낼 대상: 승인 요청 일시가 있는데 정한 시간이 넘도록 `AUTHENTICATED`에 머문 행. 시간 값은 정책값으로 두고, 3-7에서 정합니다.
- 함수 기반 인덱스(이름은 후보): "승인 요청 일시가 있고 상태가 `AUTHENTICATED`인 행"만 키를 갖게 해서, 배치가 작은 인덱스만 읽게 합니다.

**사용자:** a

3-6은 A로 메모해 두었습니다. PG 호출은 트랜잭션 밖에서 하고, 결과 반영은 짧은 트랜잭션 하나(T2)로 묶습니다. 잠금 순서는 주문 → 결제 → 회원·한도 → 원장 → 예약입니다.
